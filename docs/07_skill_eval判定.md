# 07 · Skill Eval 判定

> 立档：2026-10-30 · 按 `skill-creator` 规范执行
> 方法：同一个真实需求，两个后台子代理并行跑（一个带 skill、一个不带），
> 主 session 自己写对比判定。

## 0. Eval 设置

| 项 | 内容 |
|---|---|
| 触发方式 | `task` 后台子代理，`agent_name: worker`，两个**并行** |
| 真实 prompt | 4 个问题：达标率口径 / 艺术字是缺陷还是限制 / 子进程日志走 PIPE 还是文件 / 逐张对比做成什么形式 |
| 产出 | `%TEMP%\eval-layout-restore\with-skill.md`（21.6KB）、`baseline.md`（27KB） |
| 附带 | 两个 agent 各自写了 6~10 个诊断脚本（`_agg.py` `_dedup*.py` `_stroke*.py` `diag_artfont.py` `diag_sizes.py` `diag_caliber.py`） |

**为什么选这个 prompt**：它测的是**判断力**而不是像素 —— 批量跑 50 张要 110 分钟，
eval 扛不住；而且这 4 个问题恰好覆盖 skill 里最值钱的部分（口径 / 判据 / 踩坑 / 产物形态）。

---

## 1. 判定：**mixed**（两边各有不可替代的贡献）

**不是「with-skill 全面更好」，也不是「skill 没用」。**

| 维度 | with-skill | baseline | 谁赢 |
|---|---|---|---|
| 口径论证的系统性 | 8 条理由 + 分母陷阱 + 阈值悬崖 + **加权覆盖率 36.4%** | 5 维分桶 + 多阈值敏感性 | **with-skill** |
| 超差图的分类 | **A/B/C 三分类**（11 素材限制 / 2 混合 / 1 工程缺陷 S28）+ 尺寸核查 | 指出 13 张名单与数据对不上 | **with-skill** |
| 措辞纪律 | **主动纠正「簇 ≠ 版式族」**（来自 skill 的三层模型文档） | 未提及 | **with-skill** |
| 产物形态设计 | 三层（总览/灯箱/交付包）+ 「打开源件包」按钮 | 每张独立页 + 总索引页 + 三态 + 热力图可点跳转 | **平** |
| **代码级缺陷挖掘** | 未提 | **M21 描边宽度候选集上限 6**、**verify ITEMS 硬编码**、**47/62 全 px 化**、**batch.py 正则只认 R1-R6**、**DEVNULL 吞错误**、**10 个源图丢失**、**OCR 内容错** | **baseline（碾压）** |
| 篇幅 | 21.6KB | 27KB | with-skill 更省 |

**核心结论**：
> **skill 让模型「说得更清楚、更有纪律」**（口径不糊弄、分类不乱下、措辞不误导）；
> **但 skill 也让模型「不再自己钻源码」** —— 这是 skill 的盲区，也是它必须补的。

---

## 2. with-skill 好在哪（具体到步骤/输出契约）

### 2.1 把「达标率」从 1 个数变成有口径契约的 4 个数 + 1 个补充指标

with-skill 给了 4 个数（交付/活字/有效复刻/verify）+ **文字元素加权覆盖率 36.4%**
（926 个文字元素中 337 个位于活字达标图内）。

**「加权覆盖率」是 baseline 没有的**，而且它直接回答了客户真正在意的问题：
客户要改的是**文字**，按「张数」统计会系统性高估（12 张纯产品照把交付率抬高了 0.6 个点）。

### 2.2 把「艺术字 = 素材限制」这个结论**收窄**了

with-skill 用 skill 铁律 #13 的判据做了**分区复算**（自写 `diag_artfont.py`，
重算值与流水线报告逐张相等 → 口径可信）：

| 分组 | 张数 | 非文字区差异 | 判定 |
|---|---|---|---|
| A 纯字体天花板 | 11 | 0.16~1.32% | 素材限制 |
| B 混合 | 2 | ~6% | 背景/结构残差待定位 |
| **C 纯工程缺陷** | **1（S28）** | **15.67%** | **工程缺陷** |

并且它**主动纠正了我给的数字**：14 张超差图里**只有 7 张真的有 85px+ 元素**，
另一批最大字号只有 30~82px（参数表，残差是「大量小元素逐个累积」）。
→ 我之前说的「13 张都是艺术字」**不准确**，会把 S28 这种真缺陷糊弄成「素材就这样」。

### 2.3 用了 skill 里「簇 ≠ 版式族」这条知识

with-skill 主动警告：「这些簇是自动聚类的**视觉明暗/密度**分组，**不等于版式族**，
汇报时不要写成『覆盖 N 个版式族』」。
这条来自 `references/三层模型与版式族.md` —— **baseline 没有**，它直接把簇当成了版式族。

**这就是 skill 该起的作用：拦住一个会误导人的说法。**

## 3. baseline 为什么在某些方面更强（skill 的盲区）

baseline 没有 skill 引导，反而**自由地钻进了源码和像素**，挖出 5 个真缺陷：

| # | 缺陷 | 影响 | skill 里有没有 |
|---|---|---|---|
| 1 | `autospec.py` 的 `stroke-width` 候选集上限只有 **6** | 原图描边单侧 4~5px（SVG 要 8~10）→ **选都选不出来**；M21 的 20.07% 里约三成来自描边没画够 → **是工程缺陷不是素材限制** | ❌ 没有 |
| 2 | **47/62 交付样本把全部文字 px 化了** | 像素层版 0% 差异是**构造出来的**，不能当达成度报 | ❌ 没有 |
| 3 | `verify.py` 的 `ITEMS` 硬编码 R1~R6 | **67 个交付包从未被验收过** | ❌ 没有 |
| 4 | `batch.py` 的 `list_specs()` 正则 `^(R\d+)\.json$` | 这批 50 张在结构上**不可能**由 batch.py 驱动；且没留原始批次记录 | ❌ 没有 |
| 5 | `make_overview/make_report` 用 DEVNULL 且**不查 returncode** | 子进程失败也报「已更新」 | ❌ 没有 |

外加两个环境问题：**10 个原始素材文件已丢失**（`版式工程\refs\` 不存在）；
**OCR 内容错**（`htest`、`ALPACINO SCAREACE`）—— diff 指标查不出来这类错。

**为什么 skill 反而没让模型发现这些？**
skill 教的是「怎么判文字/怎么算达标率/怎么跑批」，这些代码级缺陷（候选集上限、
硬编码清单、DEVNULL）**不在 skill 的覆盖范围内** → 模型按 skill 的 procedure 走，
自然就不会绕去看源码。

> **教训**：skill 的 procedure 要包含一条**「产物异常时必须去读源码验证」**的强制步骤，
> 而不是只给「怎么跑」的指令。

## 5. 要不要 bundle 脚本？—— **要**

**判定依据**（`when-to-bundle-scripts.md` 的标准）：
两个 worker **各自独立写了同一类辅助脚本**，且全是「跑同样输入得同样输出」的确定性本地计算：

| 两个 agent 各自写的 | 共同点 | 该 bundle 成 |
|---|---|---|
| `diag_artfont.py` / `_agg.py` | 分区差异复算（文字区 vs 非文字区） | `scripts/diag_regions.py` |
| `_stroke.py` / `_stroke2.py` | 描边粗细/颜色实测（游程众数 + 腐蚀法） | `scripts/diag_stroke.py` |
| `diag_sizes.py` / `diag_caliber.py` | 字号分布 / 加权覆盖率 / 分母敏感性 | `scripts/diag_coverage.py` |

**token 消耗**：with-skill 21.6KB vs baseline 27KB —— **with-skill 更省**，
因为口径不用重新推导。没有「2× token 换质量」的问题。

**结论**：这三个诊断脚本该固化进 skill，让「超差图分类」变成流水线的**标准环节**
而不是每次手写。这也是把「艺术字 = 素材限制」这个**过早结论**挡在后面的机制。

---

## 6. 一句话结论

> **skill 让模型说得更清楚、更有纪律，但也会让它不再自己钻源码。**
> 所以 skill 的 procedure 不能只写「怎么跑」，必须写
> **「产物异常时去读源码验证」**，
> 并且把「分区复算」做成脚本 —— 让「艺术字是素材限制」这种结论，
> 必须先有**分区数据**才能说出口。
