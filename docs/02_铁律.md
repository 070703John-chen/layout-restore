# 02 · 铁律

> 每一条都是踩坑换来的。**动手改引擎之前先读完。**

---

## 1. 挖字掩膜用「文字自身 fill 色」

不用「与区域众数色差异大」。
小区域里众数色会被文字本身带偏 → 把胶囊底 / 横幅底 / 价卡底一起挖掉 → 渲出来是白块。

---

## 2. 背景回填用「留出法」选算法

- inpaint 适合纯色面板上的小字；多项式适合大号字压在渐变上（inpaint 会拖糊）。
- 判据**不能**是「重建 vs 原图」—— 原图那格是**字**不是背景，越像字越"准"，是自欺欺人。
- **留出法**：在元素附近随机挑一批**已知是背景**的像素，假装它们也被挖掉了，
  看两种算法谁能更准地还原它们，谁赢就派给真正的文字区。
- **考题厚度要跟真实难度一致**：真实要补的是粗笔画的洞（大字笔画十几 px 宽），
  用单像素考 inpaint 等于送分。考题按元素高度估笔画粗细膨胀。

---

## 3. 寻优的「当前值」必须进候选集

否则**越寻越差**：候选里没有现值时，最优解必然比现值差，引擎却照样把它写进 HTML。
（R2 首次寻优时 y 被从 125 改成 127，误差反增。）

---

## 4. 通道顺序错了，灰色样本验不出来

`hex → 像素` 先后写成 G,R,B 和 B,G,R 两种错法。灰白色（#FFFFFF/#111111）三通道相同，
错了也看不出来；一到红色系（#AD0E19）就**整片挖不出来**。

> **颜色相关代码必须用彩色样本验。**
> 本项目图像数组一律 RGB（PIL 读进来的）；cv2 那条线才是 BGR。

---

## 5. 负结果也记：掩膜扩张（`grow`）六张图全部变差

想法：大字的抗锯齿边缘会残留成鬼影 → 多膨胀 1~2px 吃掉边缘。
实测全部变差 —— 吃掉边缘也吃掉了周围背景，inpaint 的洞更大 → 糊更多。
参数保留但默认关闭。

---

## 6. 交付前必须跑验收脚本对账

`verify` 渲的是「客户拿到包之后打开的效果」，不是中间目录。中间目录对账会漏掉问题。

第一次跑就抓到两个回写 bug：

- **同名文字用 `hits[0]` 匹配** → 两处同名文字全写成第一处的值
  （活字版 4.16% → 5.18%）。修法：按出现顺序逐个消费命中（HTML 顺序 = spec 顺序）。
- **文本含 `&` 时 HTML 里是 `&amp;`** → 匹配不上，寻优值没回写。
  修法：marker 统一存**原文**，匹配时统一转义一次。

## 7. 判「墨色」不能只用「离单一全局底色最远」★

**底色是局部量，不是全局常量。**

### 现象

文字**横跨两种底色**时（电商图极常见：文字压在色块 / 半透明蒙版的边界上），
「离全局底色最远」抓到的是**另一种底色**，不是字。

实测：参数档案卡上「锅身容量：2.5L」「额定功率：1000W」两行横跨
浅米底 `#CEC4B1` 与深棕块 `#463D37`（边界 x=530）。

```
bg_hex = 框内最大簇            → 浅米 #D0C7B9
d = |像素 - bg|.max            → 深棕底 距离 150
                                → 白字    距离  70
dmax=150 → thr=0.75*150=112   →「最远的墨」= 深棕**底色本身**
字色 = #453D37（底色）
→ 掩膜规则是「与 fill 接近的像素全挖」→ 挖掉的是**背景**，留下的是**白字**
→ 再把字重绘成深棕 → 出现「黑色粗体 + 白色鬼影」
```

### 修法（三段式）

| 段 | 做什么 | 为什么 |
|---|---|---|
| ① **局部底色** | 逐列估底色，参照**框外上下条带** | 框内众数在粗体大字上会被笔画污染（整列都是笔画，众数=字色） |
| ② **硬边界检测** | **连续切分**（枚举切点 + 两段残差校验） | 「排序后找最大间隙」会把徽章边缘这种锯齿状边界误判成两段 |
| ③ **厚度判据** | 连通块「腐蚀到消失的次数」= 厚度；只保留**细**的（笔画），剔除实心色块 | 笔画几 px 粗，色块几十 px 粗 —— **颜色分不开时厚度能分开** |

### ★ 最关键的落地教训：新判据先当「仲裁者」，不当主力

把「厚度判据」直接当主判据去取字色 → **照片底上的字全部取浅**
（高光纹理混进来了，实测两族字色集体变浅）。

正确用法：

```
老路「离全局底色最远」算出的字色  ==  某一列的局部底色（差 < 30）
   → 说明它抓的是「另一种底色」而不是字
   → 这时候才让厚度路接管
```

### 验收方式

**端到端重跑比 `_report.json` 指标 —— 新旧 spec 的颜色不能直接比**
（旧的是寻优后回写的值，新探针给的是寻优前原值，两者不可比）。

## 8. 取色探针的三个模式，用错就翻车

| 模式 | 底色怎么定 | 什么时候用 |
|---|---|---|
| `ring` | 框外一圈的中位色 | 海报、纯色底 |
| `majority` | **框内**像素的最大簇 | **电商图必需** |
| `majority` + 局部底色仲裁 | 逐列局部底色 | 文字跨底色时 |

**为什么电商图必须用 majority**：深紫标题条上的白字，框外一圈（扩 40%）大半是下方白底 →
ring 的中位色算成浅色 → 「离它最远」= 深紫 → **字色取反**，白字被画成深紫，
落在深紫条上直接看不见。

## 9. 纯黑墨色不能被显式跳过

量化取簇时如果 `if 饱和度==0 and 明度==0: continue`，那「型号」这种真黑小字
（实测原图 `#010101`）永远进不了候选 → 探针只能给抗锯齿中间灰 `#868686`
→ 重建出来整片发灰。

**正确做法**：背景色已知 → 找**离背景最远**的那批像素（笔画核心）→ 取其中位色。
不管它是不是纯黑。

小字里灰色边缘像素本来就比黑色核心多，按「簇占比」挑一定会挑中灰。

## 10. 形态学闭运算会把白字桥接进色块

闭运算 9×9 核足以跨过 3~6px 宽的字，把色块上的白字「填」进掩膜 →
白字被算进色块，色彩离散度从 4 飙到 39 → **真色块反被误杀**。

修法：取色用**原始 bin 像素**，不用闭运算后的掩膜；
粗糙度判据从边缘算子换成色彩离散度。

## 11. Windows 上三个必踩的坑

### 11.1 中文路径 → `cv2.imread` 失败

用 `np.fromfile + cv2.imdecode`；写图用 `cv2.imencode + tofile`。

### 11.2 控制台 GBK → `UnicodeEncodeError` 直接崩整轮

寻优日志里有中文和 `®` 这类符号，`print(marker)` 在 GBK 控制台抛异常。

**两边都堵**：引擎侧 `sys.stdout.reconfigure(encoding="utf-8")` +
调用方给子进程注入 `PYTHONIOENCODING=utf-8`。只堵一边还会漏。

### 11.3 子进程走 `PIPE` → **死锁**

Windows 管道缓冲约 64KB。子进程输出用 `PIPE` 而父进程**直到最后才读**，
日志一大就写满 → 子进程阻塞等读 → 父进程等子进程 → **永久卡住**。

修法：子进程输出**直接写日志文件**。

## 12. 批量子进程的并发纪律

- 不要在 codex 目录落临时文件：固定文件名 + 并发会互相删 → 静默返回 0 框
- OCR 直接把 ndarray 喂进去，不落任何文件
- 同一套阈值跨 3 个版式体系必翻车 —— **按族标定，不要做通用视觉引擎**

## 13. `--keys` 这类列表参数一定要按逗号切

忘了切 = 遍历字符串的**每个字符** → `'T'` 被当族名 → `refs/T*` 匹配到
`TB_F1_sec_005.jpg` → 在乱跑垃圾任务，产物全是垃圾，而且**看起来在正常跑**。

这类 bug 单测很难发现，因为「参数没报错」。批量跑一次就暴露。

## 14. ★ 自检也会骗人 —— 必做「内容级」检查 ★

**2026-10-30 一天挖出四条「表面验收 100% 通过、实际全错」**：

| 坑 | 表面验收 | 实际 |
|---|---|---|
| 像素层降级 | build exit 0，打印「验收」结论 | `index_px.html` 里 **0 张 px 素材**，像素层版 == 活字版 |
| 验收闸门 | 打印「全部一致 [OK]」，exit 0 | **根本没比对**（包里没基准），交付件被改坏也放行 |
| 发布前体检 | 打印「残留问题 0 处」 | **7 条本机绝对路径**躺在 config.yaml 里（体检只匹配反斜杠） |
| 对比站热力图 | 文件 50/50 在、链接全对 | **50 张内容全是 M01 的**，49 张张冠李戴 |

**规矩**：
1. **同批次产物哈希唯一** —— 重复即张冠李戴。
2. **报告文件 mtime 真的更新了** —— 别只看 stdout。
3. **故意破坏一个交付件，看验收会不会 FAIL** —— 不会 = 闸门是摆设。
4. **发布前体检要有「阴性对照」** —— 故意塞一条已知违规，看它能不能抓到。
   没有阴性对照的「0 残留」不可信。

**推论**：「看起来成功」和「真的成功」是两件事，必须用**产物**判定，不用返回值判定。

## 15. 退出码不能当业务信号用

`pixel_fallback.py` 原来 `return len(changed)` → 退出码 = 降级处数（实测 26）；
调用方判 `if rc == 0 and "像素层" in out` → **恒为假** → 像素层版从没真正生成。

**规矩**：
- **退出码只表达「成功/失败」**；业务结果（降级几处、差异多少）走**标记文件**。
- 不要用「stdout 里有没有某个关键词」当判据 —— 改文案就失效。
- 判断「某步骤有没有真的做」，看**产物**。

## 16. 交付包必须自带验收基准

交付源件包里**必须有 `_report.json`**（重建时算出的指标）。
没有它 → `verify.py` 取不到期望值 → 只能渲染不能比对 → 永远「全部一致 [OK]」。

**规矩**：拿不到基准 = **没验**，要判 FAIL，不能当「跳过即通过」。

## 17. 一个产物对应一批输入时，必须按**输入标识**定位产物

`make_site.py::_find_heatmap` 原来「遍历交付目录，找到第一个热力图就返回」→
遍历顺序按目录名排序 → **每张卡片都拿到 M01 的**。

**规矩**：`for key in keys: find_artifact(key)` 里的 `find_artifact` 必须**按 key 定位**；
定位失败要**报出来**，不能悄悄返回第一个能用的。

## 18. 坏配置要崩，不要静默降级

`config.py` 的 `load()` 在 YAML 解析失败时 `except: return None` → 换下一个候选 →
用户改坏配置却**零告警**，脚本拿默认路径跑，**全跑错地方**。

**规矩**：读配置失败 → **报错退出**。静默降级比崩掉更糟：
崩了 1 秒就知道，静默降级会浪费几小时跑错地方。
