# 铁律 · 踩坑换来的硬规则

> 执行前扫一眼。每条都对应一个**真实踩过的坑**，不是理论。
> 违反其中任何一条，都会复现对应的失败模式。

---

## 1. 挖字掩膜用「文字自身 fill 色」

不用「与区域众数色差异大」。
小区域里众数色会被文字本身带偏 → 把胶囊底 / 横幅底 / 价卡底一起挖掉 → 渲出来是白块。

## 2. 背景回填用「留出法」选算法（inpaint vs 多项式）

- inpaint 适合纯色面板上的小字；多项式适合大号字压在渐变上（inpaint 会拖糊）。
- 判据**不能**是「重建 vs 原图」—— 原图那格是**字**不是背景，越像字越"准"，是自欺欺人。
- **留出法**：在元素附近随机挑一批**已知是背景**的像素，假装它们也被挖掉了，
  看两种算法谁能更准地还原它们，谁赢就派给真正的文字区。
- **考题厚度要跟真实难度一致**：真实要补的是粗笔画的洞（大字笔画十几 px 宽），
  用单像素考 inpaint 等于送分。考题按元素高度估笔画粗细膨胀。

## 3. 寻优的「当前值」必须进候选集

否则**越寻越差**：候选里没有现值时，最优解必然比现值差，引擎却照样把它写进 HTML。

## 4. 通道顺序错了，灰色样本验不出来

`hex → 像素` 先后写成 G,R,B 和 B,G,R 两种错法。灰白色三通道相同，错了也看不出来；
一到红色系就**整片挖不出来**。
**颜色相关代码必须用彩色样本验。**
本项目图像数组一律 RGB（PIL 读进来的）；cv2 那条线才是 BGR。

## 5. 取色不能只用「离单一全局底色最远」★

**底色是局部量，不是全局常量。**

文字横跨两种底色时（压在色块 / 半透明蒙版边界上，电商图极常见），
「离全局底色最远」抓到的是**另一种底色**而不是字 → 字色被取成底色。

实测算式（F11 参数档案卡，横跨浅米 #CEC4B1 与深棕 #463D37，边界 x=530）：

```
bg_hex = 框内最大簇        → 浅米 #D0C7B9
d = |像素 - bg|.max        → 深棕底 距离 150 ；白字 距离 70
dmax=150 → thr=0.75*150=112 →「最远的墨」= 深棕**底色本身**
字色 = #453D37（底色）
→ 掩膜规则是「与 fill 接近的像素全挖」→ 挖掉的是**背景**，留下的是**白字**
→ 再把字重绘成深棕 → 出现「黑色粗体 + 白色鬼影」
```

### 修法（三段式，引擎已实现）

| 段 | 做什么 | 为什么 |
|---|---|---|
| ① 局部底色 | 逐列估底色，参照**框外上下条带** | 框内众数在粗体大字上会被笔画污染（整列都是笔画 → 众数=字色 → 误判跨底色） |
| ② 硬边界检测 | **连续切分**（枚举切点 + 两段残差校验） | 「排序后找最大间隙」会把徽章边缘这种锯齿状边界误判成两段 |
| ③ 厚度判据 | 连通块「腐蚀到消失的次数」= 厚度；只保留**细**的（笔画），剔除实心色块 | 笔画几 px 粗，色块几十 px 粗 —— 颜色分不开时厚度能分开 |

### ★ 关键：厚度判据只能当「仲裁者」，不能当主力

当主力 → **照片底上的字会集体取浅**（高光纹理混进来）。
正确用法：

```
老路「离全局底色最远」算出的字色 == 某一列的局部底色（差 < 30）
   → 说明它抓的是「另一种底色」而不是字
   → 这时候才让厚度路接管
```

## 6. 取色模式：电商图必须 majority

| 模式 | 底色怎么定 | 什么时候用 |
|---|---|---|
| `ring` | 框外一圈中位色 | 海报、纯色底 |
| `majority` | **框内**像素最大簇 | **电商图必需** |

为什么：深紫标题条上的白字，框外一圈（扩 40%）大半是下方白底 → ring 的中位色算成浅色 →
「离它最远」= 深紫 → **字色取反**，白字被画成深紫，落在深紫条上直接看不见。

## 7. 纯黑墨色不能被显式跳过

量化取簇时如果 `if 饱和度==0 and 明度==0: continue`，真黑小字（实测原图 `#010101`）
永远进不了候选 → 探针只能给抗锯齿中间灰 `#868686` → 重建出来整片发灰。
**正确做法**：背景已知 → 找**离背景最远**的那批像素（笔画核心）→ 取中位色，不管是不是纯黑。

## 8. 形态学闭运算会把白字桥接进色块

闭运算 9×9 核足以跨过 3~6px 宽的字，把色块上的白字「填」进掩膜 →
白字被算进色块，色彩离散度从 4 飙到 39 → **真色块反被误杀**。
修法：取色用**原始 bin 像素**；粗糙度判据从边缘算子换成色彩离散度。

## 9. 交付前必须从**交付包**重渲对账

验收要验的是「客户拿到包之后打开的效果」，不是中间目录 —— 中间目录对账会漏问题。
（首次跑就抓到两个回写 bug：同名文字用 `hits[0]` 匹配 → 两处同名文字全写成第一处的值；
文本含 `&` 时 HTML 里是 `&amp;` → 匹配不上，寻优值没回写。）

## 10. Windows 三个必踩的坑

### 10.1 中文路径 → `cv2.imread` 失败
用 `np.fromfile + cv2.imdecode`；写图用 `cv2.imencode + tofile`。

### 10.2 控制台 GBK → `UnicodeEncodeError` **整轮崩掉**
引擎日志里有中文和 `®` 这类符号，GBK 下 `print` 直接抛异常。
**两边都堵**：引擎侧 `sys.stdout.reconfigure(encoding="utf-8")` +
调用方给子进程注入 `PYTHONIOENCODING=utf-8`。只堵一边还会漏。

### 10.3 子进程走 `PIPE` → **死锁**
Windows 管道缓冲约 64KB，日志一大就写满 → 子进程阻塞等读 → 父进程等子进程 → 永久卡住。
**子进程输出直接写日志文件。**

## 11. 批量跑要按「版式簇」选片，不要随机抽

随机抽 → 一堆长得差不多的 → 达标率被相似图稀释，测出来的数字代表不了真实水平。
按版式簇分配配额 + 簇内最远点采样，才能测出跨版式的真实水平。

## 12. 达标率必须报三条口径

单报一个会骗人：

| 口径 | 含义 | 为什么单报它会骗人 |
|---|---|---|
| **交付达标率** | 活字或像素任一达标 | 交付本来就给两个版本，这才是「能不能用」 |
| **活字版达标率** | 活字版自身达标 | 反映「文字能多接近原样」 |
| **有效复刻达标率** | 只统计文字元素 ≥N 的图 | 纯产品照差异率≈0 是因为**没活干**，算进去等于放水 |

## 13. 艺术字是素材限制，不是工程缺陷

字号 85~201px 的商业展示字体（综艺体等）本机没有授权源 → 替代字体字形必然对不上。
**判断方法**：看差异热力图 —— 残差 **100% 集中在文字上**、非文字区 **0 差异**
→ 分层是干净的，差的是字体。

真要提升活字版达标率，正确的路是**把艺术字归入美术素材层**（从原图裁切贴回，
两个版本都像素一致），代价是那几处字不再可编辑 —— 但艺术字本来也不可编辑。

## 14. 列表参数一定要按分隔符切

忘了切 = 遍历字符串的**每个字符** → `'T'` 被当族名 → `refs/T*` 匹配到
`TB_F1_sec_005.jpg` → 在乱跑垃圾任务，而且**看起来在正常跑**。
这类 bug 单测很难发现，批量跑一次就暴露。

## 15. 色彩通道/编码类代码必须用彩色样本 + 彩色日志验

灰白样本（三通道相同）会让通道顺序错误隐形；GBK 控制台会让中文/符号日志隐形。

## 16. 「艺术字 = 素材限制」这个结论必须先有分区数据才能下 ★

**2026-10-30 eval 实测打脸**：先前说「13 张超差图是艺术字，素材限制」。
分区复算（非文字区差异率）之后：
- 11 张非文字区 0.16~1.32% → 确实是素材限制
- 2 张非文字区 ~6% → 混了背景/结构残差
- **1 张（S28）非文字区 15.67%、残差占 48.2% → 纯工程缺陷**

而且 **14 张里只有 7 张真的有 85px+ 元素**，另一批最大字号只有 30~82px
（参数表，残差是「大量小元素逐个累积」，不是一根艺术字笔画）。
→ 说「13 张都是艺术字」会把 S28 这种真缺陷糊弄成「素材就这样，改不了」。

**规矩**：下「素材限制」这种结论前，必须先做**分区复算**（文字区 vs 非文字区差异率）。

## 17. 描边是可修的工程项，别当成「字体还原不出来」

实测某图原图是**白字面 + 纯黑粗描边**（单侧 4~5px，SVG `stroke-width≈8~10`），
而探针把「黑+紫」的抗锯齿混色当成描边色，交付写成 `stroke-width="1"`。
→ **描边宽度候选集上限只有 6 → 根本选不出来**，这部分残差是纯工程缺陷
（占该图 20% 误差的约三成）。

**规矩**：粗描边字要同时实测**描边粗细**和**描边颜色**，两者都要进寻优候选集。

## 18. 像素层的 0% 差异可能是**构造出来的**

实测 36/50 交付样本**每个文字元素都被 px 化**（换成原图裁切块）→
像素层版当然逐像素相同（PSNR 138dB），但那是「没做活」，不是质量。

**规矩**：报「像素层版达标率」时，必须同时报「**全部文字已像素化**」的样本数，
否则这个数没有意义。

## 19. 验收清单不能硬编码样本

`verify.py` 的 `ITEMS` 写死 R1~R6 → **67 个交付包从未被验收过**，
而报告里写着「verify 自洽率 100%」。
**规矩**：验收必须遍历**实际产物目录**，不允许硬编码样本清单。
同理 `batch.py` 的 `list_specs()` 正则 `^(R\d+)\.json$` 只认 R1~R6
→ 那批 50 张在结构上根本不可能由它驱动。

## 20. 不要用 DEVNULL 吞错误

`stdout=DEVNULL` 且不查 `returncode` → 子进程失败也报「已更新」。
**规矩**：子进程要么写日志文件（可查），要么收 stdout 且**必须查 returncode**。

## 21. ★ 自检也会骗人 —— 交付前要做「内容级」检查 ★

**2026-10-30 一天挖出三条「表面验收 100% 通过、实际全错」**：

| 坑 | 表面验收 | 实际 |
|---|---|---|
| 对比站热力图 | 文件 50/50 在、链接全对、按钮能点 | **50 张内容全是 M01 的**，49 张张冠李戴 |
| 报告脚本 | stdout 数字全打完了 | **.md 根本没落盘**，磁盘上是旧文件 |
| 交付包验收 | 打印「全部一致 [OK]」 | **根本没比对**（包里没基准），坏件也放行 |

**规矩（交付前必做三条）**：
1. **同批次产物哈希唯一** —— 重复即张冠李戴。
2. **报告文件 mtime 真的更新了** —— 别只看 stdout。
3. **故意破坏一个交付件，看验收会不会 FAIL** —— 不会 = 闸门是摆设。

**推论**：发布前的「0 残留」自检也要先证明它**有牙齿**。
本项目的 `check_no_private_paths.py` 原来只匹配**反斜杠**形式的关键字，
而 yaml 里全是**正斜杠** → 一条都没匹配上 → 报「0 残留」，
实际 7 条本机绝对路径躺在 `skills/config.yaml` 里。
⇒ **自检脚本本身要有「阴性对照」：故意塞一条已知违规，看它能不能抓到。**

## 22. 退出码不能当业务信号用

`pixel_fallback.py` 原来 `return len(changed)` → 退出码 = 降级处数（实测 26），
调用方判 `if rc == 0 and "像素层" in out` → **恒为假**
⇒ 像素层版从来没真正生成（`index_px.html` 里 0 张 px 素材），
但 build 照样 exit 0 并打印「验收」结论。

**规矩**：
- **退出码只表达「成功/失败」**，业务结果（降级几处、差异多少）走**标记文件或 stdout**。
- 调用方不要用「stdout 里有没有某个关键词」当判据 —— 改文案就失效。
- 判断「某步骤有没有真的做」，要看**产物**，不看返回值也不看日志。

## 23. 交付包必须自带验收基准

交付源件包里**必须有 `_report.json`**（重建时算出的指标）。
没有它 → `verify.py` 取不到期望值 → 只能渲染不能比对 → 永远「全部一致 [OK]」。

**规矩**：验收脚本对**交付包**（不是中间目录）必须能拿到基准；
拿不到基准 = **没验**，要判 FAIL，不能当「跳过即通过」。

## 24. 坏配置要崩，不要静默降级

仓库 `config.py` 的 `load()` 在 YAML 解析失败时 `except: return None` → 换下一个候选 →
用户改坏了配置却**零告警**，脚本拿默认路径跑，**全跑错地方**。
本项目的 `common.load_cfg()` 是对的：解析失败直接 `SystemExit(2)`。

**规矩**：读配置失败 → **报错退出**。静默降级比崩掉更糟：
崩了 1 秒就知道，静默降级会浪费几小时跑错地方。

## 25. 一个产物对应一批输入时，必须按**输入标识**定位产物

`make_site.py::_find_heatmap` 原来「遍历交付目录，找到第一个热力图就返回」→
遍历顺序是目录名排序 → **每张卡片都拿到 M01 的**。

**规矩**：
- `for key in keys: find_artifact(key)` 里的 `find_artifact` 必须**按 key 定位**，
  绝不能靠「遍历找到第一个」。
- 交付前跑一次**哈希唯一性检查**（见铁律 21）。
- 定位失败要**报出来**，不能悄悄返回第一个能用的。

## 26. 别覆盖别人的批次清单

`pick.py` 原来无论 `--target` 多少都写 `batch_jobs.json`
→ 跑一次 `pipeline.py --target 10` 就把**跑了两小时的 50 张任务清单冲掉**，
后续续跑、报告、对比站全部对不上，而且**不报错**（清单被合法覆盖了）。

**规矩**：
- 任务清单文件名**带参数量**：`batch_jobs.json`（默认） / `batch_jobs_<target>.json`（非默认）。
- 每个脚本加 `--jobs-file`，编排层统一算一次文件名，各步共用。
- 改批次规模前先确认当前清单会被写到哪。

## 27. 聚类特征别用 OCR，用形态学代理 ★

**2026-10-30 实测**：12 维特征里 `text_lines` / `text_cover` 依赖 OCR，
800×800 图单张 **5.17s**（原实现还先放大 2 倍）→ 221 张要 20 分钟；
本机 CPU 又被交易系统占满（总 CPU 100%）→ 墙钟 1 小时。

**规矩**：
- **聚类只需要「这块图文字多不多、排得密不密」，不需要认字**
  → 用形态学代理（自适应阈值 → 连通块 → 筛扁宽笔画 → 按 y 合并成行），~20ms/张。
- **代理特征只能用于分组，不能用于任何对外指标。** 达标率仍走真实引擎指标。
- **先分段计时再优化**：我一开始以为慢在 cv2，实测 cv2 部分加起来 < 0.1s，
  瓶颈 100% 在 OCR。**不测就优化 = 优化错地方。**
- **特征提取一律缓存**（按输入文件集合判失效）；
  ⚠ 特征里有 numpy 标量，`json.dump` 要挂 `default=lambda o: o.item()`。
- **本机 CPU 是共享资源**：跑批前看
  `Get-Counter '\Processor(_Total)\% Processor Time'`，100% 就别开大 jobs。

## 28. ★「取 top-N 簇」会把细字的核心色挤掉 —— 候选池决定下游上限 ★

**2026-10-31 实测**：美食批次 7 张超差。原图**白字**，还原成灰/深色字。
分区复算：非文字区差异 < 1%（分层没问题），残差 92~99% 在文字区。

**根因链**：
1. `dominant_colors` 只返回 **top-8 簇** → **纯白（细字的核心色）不在 top-8 里**；
2. 候选池 `alts` 里因此**没有白**；
3. `--cal-fill` 寻优「没有正确色可选」→ 错色被**定死**，寻优也救不了。

**规矩**：
- **「取 N 个候选交给下游挑」的机制，N 决定下游的能力上限。**
  正确值一旦被 N 挤掉，下游再强也没用。
  ⇒ 候选池必须包含**由不同判据独立算出的**值，
  不能只依赖单一聚类（这里补的是「离背景最远像素的中位色」）。
- **不要在上游猜「哪个结果对」** —— 上游没有信息，只有下游（按像素差比对）有。
  把选择权交回下游。
- **改判据前先做全量回归**：新旧逻辑在**所有**样本上跑一遍，逐个比「新旧 vs 真值」。
  我第一版改法（仲裁处加硬阈值）单看目标案例是好的，全量回归却是 65 好 / 13 差。
- ⚠ **「独立真值」方法本身也可能不可靠**（我踩过：框内最大簇选错时它同样错）
  → **最终判据是「重跑后的差异率」，不是任何离线指标**。

## 29. 删除任何目录前，必须**逐文件自证覆盖**，不能按目录名/文件名推断

删掉一个「已经被归集站收走了」的工作目录之前，要证明它真的被覆盖了。
判据必须是四选一，逐文件判，判不了就**阻塞**：

| # | 判据 | 可否删 |
|---|---|---|
| ① | 目标站存在 **同名 + 同尺寸 + 同 md5** 的副本 | 可删（重复） |
| ② | 属于已知中间产物（渲染中间图 / 诊断目录） | 可删（可重建） |
| ③ | 属于「被淘汰的旧版本条目」（同图有重做版入选） | 先把配方/报告/HTML 归档再删 |
| ④ | 目标站无副本，但目标站该条目的 HTML **不按相对路径引用它** | 可删（冗余资产） |
| ⑤ | 以上都不是 | **阻塞，不许删** |

★ **两个真会翻车的索引坑**：
- 建索引时用 `len(rel) >= 3` 才收录，会把 `<目录>/<条目>/index.html` 这类
  **顶层文件全漏掉**（它们的 rel 长度是 2）。
- 判「HTML 是否引用某资产」按 **basename** 匹配，会把 `诊断目录/assets/x.png`
  误当成被引用的 `assets/x.png` ⇒ 必须按**相对条目目录的路径**匹配。

★ 覆盖度 < 100% 的东西**只能归档，不能删** —— 「看起来是冗余」不是删除理由。
★ 磁盘占用要**按 inode 去重**统计，否则硬链接会被重复计数。

## 30. 删掉工作目录后，必须给「生成脚本」加**源缺失闸门**

出站/归集脚本的数据源通常就是那个被删掉的工作目录。
清理之后谁要是直接重跑，**会把已经建好的成品静默覆盖成空站** —— 不是报错，是产出空站。

```python
if not os.path.isdir(SRC_OUT):
    print("[ABORT] 源目录不存在（已清理）。未改动任何产物。")
    print("        正确顺序：① 跑引擎生成源目录 → ② 跑归集 → ③ 跑出站")
    return 2
```

★ 守卫要写在**任何写盘动作之前**，并用 `sys.exit(main() or 0)` 把返回码传出去。
★ 验收方式：故意重跑，确认退出码非 0 **且成品文件字节数前后完全一致**。

## 31. 交付页的「坏图」判定必须限定**当前可见的图**

`loading="lazy"` + 折叠容器 ⇒ 浏览器**永远不发起请求**，`naturalWidth` 必为 0
⇒ **不是坏图**。不限定就会误报一大片。

- 坏图只判**可见图**（`offsetParent !== null`）；折叠项**展开后单独再验一遍**。
- 磁盘级存在性检查要用**浏览器解析后的绝对 URL**（`img.src`），
  **不能用 `getAttribute('src')`**（那是原始相对路径，会把整页都报成「缺文件」）。
- 等待图片加载**必须加超时**且**只等可见图** —— 被折叠的 lazy 图永远不触发 `load`，
  无超时的 `Promise.all` 会死等。

## 32. 采集图与生成图放**同一个页面**，并提供「按图位 / 按产品」双视图

- 一个页面里同时有采集图与生成图，每条一行 **采集图 | 生成图 并排**。
- 提供两个视图：**按图位**（主图/附图…，二级=产品）与**按产品**（组内=图位）。
  「分主图附图」和「同产品在一处」两个诉求用两个视图同时满足，不必二选一。
- 灯箱里左右键在**采集图 ↔ 生成图**之间切换，不用退出灯箱再点另一张。
- 专科页面用 `../assets/` 相对路径引用全站图 ⇒ 零重复拷贝，仍是「一个存放目录」。

## 33. ★ 商业字体**绝不入库**；每个入库字体必须随附**许可全文**

- 商用字体（Monotype 等）的授权写明「受许可协议约束、不得再分发」
  ⇒ 进公开仓库等于侵权分发。**第一个 commit 就带进去的也算数**，
  只删工作树文件没用，git 历史里还在。
- 引擎要把这类字体登记为「可选」：**只有使用者自己放了字体文件才启用**，
  没放就自动降级到仓库自带的开源字体；`@font-face` 也只对**真实存在**的文件生成。
- 开源字体（Noto / Playfair 等，SIL OFL 1.1）**必须随附许可全文**，
  缺了 OFL.txt 就是不合规分发。许可正文直接取自上游（Google Fonts），
  不要手写。
- 自检脚本要能**自动发现**这类问题：读字体 name table 的版权行与许可行，
  识别「无开源授权」的字体并报错。

## 34. ★ 可变字体（VF）的「默认实例」随渲染库版本变化 ⇒ 产物不可复现

- 可变字体（如 `NotoSansSC-VF.ttf`）没有稳定的「默认字重」：
  渲染库（Pillow）会自己挑一个默认实例，**不同版本挑的不一样**
  （本机 Pillow 9.5.0 挑的是 `Thin` 极细体）。
- 后果：同一份代码 + 同一份字体，在不同 Pillow 版本下**渲染出的字形完全不同**
  ⇒ ① 生成的示例图/产物图 md5 对不上，CI 的「示例图可复现」必红；
  ② 差异率数字不可比。
- 修法（按场景选）：
  - 要**跨环境字节级可复现** ⇒ 精确锁渲染库版本（`Pillow==9.5.0`），
    并把当次生成的产物提交进仓库，让「仓库内产物 == 重跑产物」成立；
  - 不想被库版本绑架 ⇒ 示例图改用**静态字体**（固定字重的单实例文件），
    或渲染时显式指定 weight（Pillow 10+ 的 variation API）。
- ⚠ **这条坑的隐蔽性来源**：仓库长期「CI 绿灯」的假象，其实来自
  「仓库从未 push ⇒ GitHub Actions 从未跑过」。
  ⇒ **CI 配置本身也是未验证代码**：第一次推上去之前，
  先在本地把 CI 的每一步都跑一遍。

## 35. ★ 抗锯齿晕圈 ≠ 描边；同色描边 = 纯加粗（会把字撑成糊块）

- **症状**：活字版（可编辑版）里某几行字「糊成一坨白块/色块」，读不出来；
  而像素层版完全正常 ⇒ 一定不是「素材/字形」问题，是**描边被误加**。
- **成因链**（2026-11-09 实测，demo_param_card）：
  1. 细体字在浅色底上，抗锯齿产生一圈「墨色↔底色」的**插值色**；
     它**离底色也远** → 探针的启发式「第二簇离底色也远 ⇒ 当描边」把它判成真描边；
  2. `fill` 与 `stroke` 有时**同色** —— 这层描边语义上等于「加粗」；
  3. 描边宽度寻优的打分器量的是「接近描边色的像素数」（tol=90），
     而**填充色本身也落在这个容差里** → 描边越宽得分越高 → 永远挑最大值（12px）；
  4. 22~36px 的字 + 12px 描边 ⇒ 相邻字形互相重叠 ⇒ **整行糊掉**。
- **判据（可执行）**：max 范数下三角不等式 `‖S−F‖∞ + ‖S−G‖∞ ≥ ‖F−G‖∞`，
  且**当且仅当 S 落在 F→G 连线上时取等号**。
  ⇒ 抗锯齿晕圈必然「共线」（slack ≈ 0），真描边色明显偏离连线（slack 很大）。
  用 slack 判定「这是混色，不是描边」。
- **三条硬规则**：
  1. 探针：`fill == stroke` ⇒ 描边丢弃（加粗请用 `font-weight`）；
  2. 探针：第二色簇若判为混色（slack 小）⇒ 不是描边；
  3. 打分器：描边面积统计必须**排除填充色**（`exclude=fill`），
     否则「描边越宽越好」的天花板是错的。
- **通用教训**：**「离底色远」不等于「是描边」**。
  任何靠颜色距离区分「字 vs 描边 vs 底色」的判据，都必须额外排除
  「三种颜色两两之间的插值」——否则抗锯齿会冒充任何一层。
- **验收**：渲染结果必须**人眼能读**。
  差异率只是「像不像」，**读不出来 = 交付失败**，哪怕 diff 数字很好看。
  ⇒ 每次改引擎后，看一眼总览图里活字版那一列，**逐行读一遍**。

## 36. ★ 局部（patch）渲染必须平移**所有**图层 —— 否则判据被无关内容污染

- 寻优打分的局部渲染，把整页内容按 `(-x0,-y0)` 平移，让打分 region 落在视口原点。
  **平移必须覆盖每一层**：照片底板、矢量色块层、矢量线条层、文字层，
  **以及每段文字自己的美术裁片（`t00_art` 之类）**。
- 只平移「登记在 `spec["art"]` 里的图层 + 照片底板」，其余原样保留 ⇒
  那些图层在 patch 里出现在**海报原坐标**，也就是**左上角视口**里 ——
  和被打分的 region 毫无关系，却照样盖在 cell 上。
- **后果不是「多一块图」，是判据被污染**（2026-11-09 实测，demo_param_card）：
  1. 越界图层是一块深色裁片 ⇒ cell 的 `dmax`（离底色最远距离）
     从字的 91 被抬到 **181**；
  2. 墨量阈值 `thr = max(55, 0.55×dmax)` 从 55 被抬到 **99**；
  3. 字的真实对比度只有 **91 < 99** ⇒ **字自己被排除在自己的墨量统计之外**；
  4. 统计到的只剩那块深色方块，而它被越粗的字盖得越多
     ⇒ **墨量随字重递减**（100→463、900→330）；
  5. 字重打分等于在给「标题色块」打分 ⇒ 低对比度标签被选成 700/900，
     原图是细体、还原出来是黑体。
- **诊断信号（非常好认）**：**指标与直觉反向** ——「字越粗墨量反而越少」。
  ⇒ 这种反向一定是判据被污染，**不是**字重候选选错；
  先查判据口径（cell 里到底有什么），再谈调参。
- **自检**：局部渲染后，cell 的 `dmax` 应与该区域**原有内容**的对比度一致；
  若各候选的 `dmax` 明显偏大且**彼此相同**，就是有越界图层没平移。
- **修法**：图层平移按它自己的 `left/top` 走，不要「只认登记过的图层」。
- **影响面**（同批生产数据实测）：262 个交付包中 49 个（19%）、
  7256 个可打分条目中 658 个（9.1%）的判据被污染过。
  ⇒ 引擎修好后，**这批产物需要重跑**才算数。
- **通用教训**：**「指标」本身也要验口径**。
  一个算错的指标不会报错、只会安静地把结论带偏；
  看到反直觉的数字，先怀疑指标，再怀疑被测对象。

## 37. ★ 同一段文字出现多次时，寻优必须按 **tid（元素号）** 定位，不能按文字内容

- sweep 条目里带的是 `tid`（元素号，如 `t17`），但定位目标元素靠的是
  「`marker` 文字内容 + `occ`」，而 `occ` 默认取 **0**。
- ⇒ 同一段文字在图里出现多次时（电商图极常见：同一个「调味面制品」在三个位置各出现一次），
  寻优**永远改的是第一个**那个元素，而被打分的 region 属于**另一个**。
- ⇒ 被改的属性对被测区域**零影响** ⇒ **所有候选同分**。
- **后果（实测 2026-11-10，生产批 FD_CZ028_3）**：整包 20 多项 sweep 全部「0 px」，
  寻优等于没做；而旧逻辑并列时挑第一个候选 ⇒ 整包属性被写成**任意值**
  （font-weight→300、font-size→33…），且**全程无任何异常**。
- **影响面（整站实测）**：26686 个 sweep 条目里 **3597 个（13.5%）定位错**，
  **262 个交付包中 102 个（39%）**受影响。
- **修法**：
  1. `occ` 由 `tid` 换算（HTML 里 `<text>` 的顺序 = `spec["text"]` 的顺序，
     数出「第几个同文字元素」即可）；
  2. 基准色（fill/stroke）也按 `tid` 取元素 —— 按文字内容取会拿到**别的元素**的颜色；
  3. **元素在 HTML 里压根不存在**（美术块还原、不画活字）⇒ 该项寻优没有意义 ⇒ 直接跳过。
- **自检**：任何一项 sweep 如果**所有候选得分完全相同**，就是「改不动」——
  先查是不是定位错了元素，再查是不是它被美术块盖住了。

## 38. ★ 渲染失败会伪装成「完美匹配」—— 空白候选不得当成 0 分

- 打分是「与原图差异 > 20 的像素数」，**0 是最好分**。
- 而**页面没加载成功**时，候选 cell 是空白的；若原图那块也是纯色/浅色，
  空白 cell 与它的差异就是 **0** ⇒ **渲染失败被当成「所有候选都完美」**。
- **自检（两条同时成立才判失败，避免误伤）**：
  ① 所有候选 cell 都是纯色（渲染没画出东西）② 原图对应 region **不是**纯色。
- **附带**：Playwright `goto` 默认 30s 超时在机器负载高时会炸（2 核机同时跑 3 个任务必炸），
  炸了之后所有候选都是 0 分 ⇒ 改用 `domcontentloaded` + 显式等图片 `complete`，
  超时放宽到 120s。
- **通用教训**：**「0 分」有两种含义：真的完美，和什么都没渲染。**
  必须显式区分，否则失败会伪装成成功。

## 39. `dominant_colors` 的 HSV 粗量化会让「最大簇」不等于「底色」

**现象**：`probe_layers.dominant_colors()` 用 `h//15, s//85, v//85` 分桶
⇒ **暗部背景会按色相被拆成好几个小簇**
⇒ 「框内最大簇」不再等于背景。
当字是**饱和暖色**（淘宝详情页常见的金色标题）时，金色簇反而成最大簇
⇒ `majority` 模式把**字色当成了底色**。

**后果（三处同时出错）**
1. `make_plate` 按 `fill` 挖字 ⇒ 挖掉的是背景
   ⇒ inpaint 用旁边的字色把整块涂满 ⇒ **底板出现色团**
2. 渲染时字色用 `fill` ⇒ 字色渲反
3. `alts`（候选色池）=「离底色远的簇」⇒ **真字色根本不在池里**
   ⇒ `--cal-fill` 寻优**没得选**，只能瞎挑 ⇒ 选到近黑
⇒ 活字版表现为「隐形」或「重影」。

**实测**：iQOO Neo12 详情长图 29 段文字里 **8 段取反**
（「强劲/耐用/超大/低温/强劲性能/轻松应对/Neo史上最大/冰穹铠甲/整机低温感…」）
`t16 超大` 蒙对**纯属运气**（那块纯黑够纯、没被拆簇）。

**正解（不要用颜色启发式去判）**：
**把候选池补齐，让寻优按像素差自己挑。**
- 候选池 = 墨色 + 框内所有「离底色远」的簇色（上限 4~6）
- 再用「厚度保留率」兜底判墨/底（见铁律 69）

## 40. 判「墨色 / 底色」用**厚度保留率**，不要用「谁占比大」

```
ret(c) = |open(mask_c, k)| / |mask_c|,   k = 0.25 × 框高
```
- **墨迹是细结构**（笔画宽 ≈ 0.1~0.2 em）⇒ 开运算（先腐蚀后膨胀）后几乎不剩 ⇒ **ret 低**
- **底色是大块面** ⇒ 开运算后基本还在 ⇒ **ret 高**
- ⇒ **墨 = ret 最小的候选；底 = ret 最大的候选**

★ 与「亮/暗」**无关** ⇒ 亮底暗字、暗底亮字都成立。
★ 不要用 top-hat 能量判极性：小字的**笔画间隙**本身也是「细的暗结构」，
  closing 会把间隙吃掉 ⇒ 小正文（白字黑底）会被判反（实测 12 段全错）。

**采信规则（安全阀）**：只有「本判据的结论 == 原探针结论的**整对互换**」才直接改；
其余一律保留原值（只补候选池）。否则会把抗锯齿中间色、渐变也改掉。

## 41. 探针会把**实心展示字**误拆成「深色字芯 + 同色描边」

`fill_vs_stroke()` 靠腐蚀把字拆成「字芯 / 描边」。
对**实心金色展示字**会误判成「深色字芯 + 金色描边」。

**连锁放大**：`stroke-width` 寻优按**「描边面积」**打分
⇒ 把描边加粗到盖满整个字
⇒ **字色寻优的像素信号被描边淹没** ⇒ 字色只能瞎选（实测选了近黑）。

**修法**：**描边色 ≈ 墨色**（Δ≤46）⇒ 描边是假的
（SVG 里同色描边本就隐形）⇒ 删 `stroke` + 删该元素的 `stroke-width` 寻优项。
实测 36 段里删掉 20 处，删完字色寻优立刻恢复正确。

## 42. 电商图必须显式指定字体族：`--cjk-font "Noto Sans SC"`

`autospec.py::guess_font()` 是**海报启发式**（`h>30 → "Noto Serif SC"` 宋体），
它自己的 docstring 就写着：「电商图直接套会错得离谱：淘宝促销大字是**黑体**」。

⇒ 详情长图 / 淘宝主图这类**黑体展示字**场景，
**不传 `--cjk-font` 就会整批渲成宋体**，字族差一整个量级。

指定黑体后只剩 `NotoSansSC-VF.ttf`。
★ 交付件体积也跟着降（宋体 25MB → 黑体 VF 17MB，且按需拷贝）。

## 43. 凡吃 spec 数值字段的引擎代码必须显式判 `None`

`t.get("text_length", 默认)` **只防缺键、不防 null**：
探针会写 `"text_length": null`（键存在、值为 null）⇒ `int(None)` 崩。

```python
_tl = t.get("text_length")
w = int(_tl) if _tl is not None else int(t["box"][2] - t["box"][0])
```
★ **不能写 `or 默认值`** —— 值=0 时语义会变（0 = 不加 textLength）。

**为什么会漏**：base 批这些元素 `cut_art()` 后仍 `art_covered=True`
⇒ 在 `continue` 分支里 ⇒ **永远到不了**出问题的行
⇒ 优化版改了 fill/weight ⇒ 美术层判定翻转 ⇒ 才崩。
⇒ **改引擎后必须回归验证「真会走到那行的元素」有多少个**，不能只看「跑通了没」。

## 44. 寻优是**顺序**跑的：颜色错了，后面的几何寻优**全是瞎选**

引擎的 `sweep()` 逐条处理 spec 的 `sweep` 列表，**每条都以上一条跑完的 HTML 继续**。
autospec 生成的顺序是：`font-size` → `y` → `x` → `stroke-width` → `font-weight` → **`fill`（最后）**。

⇒ **`fill` 排在最后 = 前面的几何/字重/描边寻优全程在错误字色下做**。

**实测故障链**（详情长图金色展示字「视效」）：
1. 探针把字色取反成黑 ⇒ 寻优跑 `font-weight` 时墨量判据
   （`inkarea` = 「渲出来的墨迹面积」）**恒为 0**（黑字压黑底）⇒ **判据全盲** ⇒ 字重被选成 **500**（该是 900）
2. 到 `fill` 时才选颜色 ⇒ 但此时**字形已经细了一圈**（500 字重），
   区域差异不管什么颜色都是 ~39% ⇒ 颜色那点差异被淹没
   ⇒ 像素差挑「差得少一点」的**底色黑** ⇒ **黑字压黑底 = 隐形**

**修法（spec 层，不用改引擎）**：修复器把 `sweep` 里的 `fill` 条目**移到最前**
⇒ 颜色先定 ⇒ 后续字重/描边寻优看到正确字色 ⇒ 墨量判据恢复 ⇒ 字重选对。

**验证方式**：修完后 `spec["sweep"]` 的前 N 项 attr 应全是 `fill`。

## 45. **像素差对颜色不敏感**（字形失配主导时）—— 取反已被证实的要**钉死**

当原图用**展示字体**（超粗黑体、3D 描边）而复刻端只有**普通黑体**时，
字形失配的像素差远大于颜色差 ⇒ **像素差判据对颜色几乎不敏感**。

实测（详情长图 1080×3586，元素 t20「视效」）：
| 字色 | 区域差异像素 |
|---|---|
| 金 `#EEB31C`（真） | 8882 |
| **黑 `#000000`（底色）** | **8673** ← 寻优选了它 |
| 浅金 `#D2AC4C` | 11503 |
| 暗金 `#785915` | 11595 |

⇒ 像素差选了**底色**，肉眼却是「隐形字」。
⇒ **判据没错，但它在这个场景下测的不是「对不对」，是「像不像」**。

**修法**：颜色**已被独立判据证实取反**（铁律 69 的厚度保留率 + 「整对互换」规则）时，
**把该元素的 fill 寻优钉死成那个颜色**（`sweep[fill].values = [真字色]`），
不让像素差寻优再翻案。

★ **前提是这个独立判据可靠**：铁律 69 的判据在长图上逐张目视验证过（29/29 正确），
所以才能钉死。**判据不可靠时不要钉死**（主批次上该判据有误判，见下）。

## 46. 「修复器」类工具的判据**必须逐样本人工验证过**才能用

## 47. 差异归因**先分「框内 / 框外」**，再谈优化

不知道差异分布就动手改参数 = 瞎试。**先做逐元素归因**：

实测（详情长图 vivoX300Ultra 1440×7816，工作副本 1051×5707）：
| 区域 | 差异像素 | 占总差异 | 该区域差异率 |
|---|---|---|---|
| **文字框内** | 273436 | **96.49%** | **39.53%** |
| 文字框外 | 9949 | 3.51% | 0.187% |

⇒ 底板重建质量**几乎完美**（框外 0.187%），
   问题**全部在文字**（框内 39.5% ≈ 每个字形都不对）。
⇒ 于是「展示字还原不了」这个判断被证伪：h≥80 的展示字**只有 1 个元素、占 1.85%**；

⇒ **结论：要修的是「所有文字」，不是「展示字」。**

**做法**：逐元素算 `|render - plate| > 30` 的墨迹量 + 逐框算 `|render - orig| > 20`，

## 48. spec 字段：**键不存在 ≠ 键为 null**，任何回写都要 null 安全

`dict.get(key, 默认值)` 的默认值**只对缺键生效**；键存在但值为 `null` 时返回 `None`。

实测踩坑（三处，引擎 `rebuild.py`）：
1. `build_html`：`int(t.get("x", t["box"][0]))` —— 键存在值为 null ⇒ `int(None)` **崩**
2. `calibrate_apply.restore()`：把「原本**没有 x 键**」的元素**写回成 `"x": null`**
   ⇒ 之后 `build_html` 崩 ⇒ **校准的「变差回退」分支必崩**
   （实测：长图每张都有元素缺 `x` 键 ⇒ 一旦触发回退，整张图失败）
3. `_sync_spec_from_html` 用 `cast=str` 回写 `base` ⇒ 存成字符串 `"628.0"`
   ⇒ 后面 `int(t["base"])` **ValueError**

⇒ **规矩**：
- 读：`v = t.get(k); x = int(v) if v is not None else 默认`（显式判 None）
- 写：回写快照时，**None 一律删键**（还原成「键不存在」），不要写成 null
- **回写类型必须和读取类型一致**（base 全程 int，不要中途变 str/float）

★ 这类 bug 的特征：**只在「异常分支」里出现**（回退 / 回写 / 异常兜底），
主路径跑 100 张都不炸 ⇒ 必须专门构造异常路径来测。

## 49. **位置对齐不能用「像素差」当判据** —— 它会奖励「把字藏起来」

实测（详情长图 556×1934，元素 t21「UFS4.0」）：
| 候选 | 该元素区域差异像素 |
|---|---|
| **把字挪出框外（等于藏起来）** | **122** ← 最优！ |
| 把字画在正确位置（字形不符） | 383 |
| 把字挪到别处 | 307 |

⇒ 原图是 **9px 高的像素风字体**，Noto Sans SC 画粗了反而错更多像素
⇒ 像素差判据**系统性偏好「不画字」** ⇒ 用它做位置寻优会把字删掉。

**正确判据 = 墨迹包围盒的位置**（与字形胖瘦无关，只看笔画落点）：
- 原图侧：在该元素的 OCR 框内（pad=0）量墨迹框
- 渲染侧：**只渲染这一个元素**（白底、无其它图层）⇒ 量它的墨迹框
  （只留目标元素 ⇒ 邻居不会污染测量）
- 打分：`|Δ左|+|Δ上|+|Δ右|+|Δ下|`

实测收益：t21 偏差 **47 → 6**、t67 **46 → 2**、t06 **44 → 5**。

★ 顺带定案了引擎 `calibrate_apply` 的结构性缺陷：
它的判据是「**纯颜色阈值 + 大 padding 窗口**」（`pad = 0.3×max(w,h)`）
⇒ 会把**邻居文字的墨迹**算进来；再加上全局迭代 + 回退语义不清
⇒ 最终状态既不是初始值也不是最优值（实测 base 被挪走 21px，字与上一行重叠）。

工具：`_align_layout.py`（逐元素墨迹对齐）、`_repair_layout.py`（像素差版，对照用）。

## 50. 文字内容对不对，要用**墨迹 IoU**，不能用差异像素数

铁律 78 的延伸：**判「文字内容对不对」**（OCR 纠错）同样不能用像素差。

**IoU 判据**：原图该框的墨迹掩码 A vs 只渲染该候选文本得到的墨迹掩码 B
⇒ `|A∩B| / |A∪B|`。
- 对字：笔画落点大体一致 ⇒ IoU 高
- 错字：笔画落在别处 ⇒ IoU 低
- **与字形胖瘦无关** ⇒ 不会像像素差那样偏向「不画」

工具：`_pick_text.py`（候选 → IoU 选优）、`_reocr_elements.py`（全分辨率重识别出候选）。

## 51. 交付页必须标注**「活字层 vs 美术层」占比**

引擎会自动把「被美术块覆盖 ≥50% 的文字」归**美术层** = 从原图裁切贴回 ⇒ **不可编辑**。
不标注就会把「原图拼回去」说成「复刻」，**夸大成果**。

实测（详情长图 15 张）：整体 活字 687 / 美术层 115 ⇒ 可编辑率 **85.7%**；
但**单图差异很大**：`vivoiQOONeo12_2160x6798` 只有 **活字 2 / 美术层 63（3% 可编辑）**，
差异率 0.3% —— 这张的「低差异率」是**因为大部分是原图裁切**，不是复刻得好。

⇒ 每行必须写「活字 N ｜ 美术层 M」；KPI 必须给「可编辑文字占比」。
⇒ **低差异率 ≠ 复刻得好**：必须和「可编辑率」一起看。

## 52. 长图的美术块探测会把**整块渐变横幅**误判成照片资产

⇒ 详情长图的整块 hero 横幅（1200×1242）、整块底部价格区都被收进美术块

⇒ 照片上会出现平涂补丁，比「不可编辑」更难看。
⇒ 正确做法：**如实标注**（铁律 80），或给美术块加**面积上限**后重跑（需评估照片重建质量）。

## 54. 做「元素独占测量」时，**测量格的底色必须 = 该元素的底色**

判据若用**相对极性**（「像素更接近字色还是底色」），测量环境的底色必须与元素真实底色一致。

实测踩坑（小米长图 t38）：`fill=#7E7E7E`（灰字）/ `bg=#000000`（黑底）。
把该元素**单独**渲染到白底格上量墨迹 ⇒ 白底像素「更接近灰」⇒ **整格都成墨迹** ⇒ 墨迹框完全失真。

⇒ 两条规矩：
1. 单独渲染时**把页面底色改成该元素的底色**（`html,body{background:<bg>}`）
2. 判据优先用**绝对色差**（`|p − 字色| < 110`）⇒ 原图侧与渲染侧口径一致；
   只有绝对阈值几乎找不到像素时，才退回极性规则

★ 推论：**任何「只测一个元素」的渲染方案，都必须交代它的底色。**
（`_align_layout.py` / `_pick_text.py` 都已按此修）

## 55. 位置/字号搜索范围要按**实测位移自适应**，不能写死窗口

固定 ±26px 窗口修不了「偏 40px」的元素。

实测（小米长图 t38）：原图墨迹在 2274–2292，而渲染画在 2250（偏 24px 以上）
⇒ 落在固定窗口外 ⇒ 搜索找不到最优 ⇒ 元素保持错位（且**隐形字体检闸**抓得到它）。

⇒ 正确做法：
1. 先量**当前渲染**的墨迹框（元素独占渲染）
2. 算出需要的位移 `dy = 原图顶 − 当前顶`、缩放 `ds = 原图墨迹高 / 当前墨迹高`
3. 把搜索**中心挪到 `base + dy`** 附近再精搜（而不是围绕当前值搜）

⇒ 修完 t38：偏差 **86 → 4**，基线 2250 → 2291。

★ 通用：**搜索范围应由「实测误差」决定，不由经验常数决定。**

## 58. 工作区外的删除/移动，**只能走 Python 脚本**，shell 工具一律被拦

实测（2026-11-09，工作区 = `<工作区>`）：

| 尝试 | 结果 |
|---|---|
| `rm -- "<本机路径>"` | `Windows trash execution rejected a target outside the workspace.` |
| `Move-Item -LiteralPath <工作区外路径>` | `recursive write/delete target cannot be verified inside the workspace` |

## 59. 交付页验收要把「**磁盘级**文件存在性」查出来，别只信浏览器

`loading="lazy"` + 折叠容器 ⇒ 浏览器里 `naturalWidth===0` 既可能是「没滚到」，也可能是「文件真缺」。

1. **滚完全页 + 展开全部 `details`** 再查 `naturalWidth===0`
2. **把每个 `<img src>` 拿去磁盘逐个 `os.path.isfile`**（相对站点根解析）⇒ 这一条才抓「链接失效」

（灯箱里的 src 是 `file:///<绝对路径>` 这种 URL 编码绝对路径，**不能直接 `os.path.join(base, src)`**，
要先 `urlparse` + `unquote` + 去掉前导斜杠。）

★ 另：站点里 `aspect-ratio` **只能写图片真实比例**（如 `1200/2974`），
用来预留高度防抖动；**绝不能写 `1/1` 强制方框**（会把竖长图压方、比例失真，看不出差别）。

## 60. 模板里 Python 侧常量**必须显式注入 JS 侧**，否则渲染会静默中断

`_make_phone_site.py` 用 Python 的 `ROLE_ORDER` 生成了 HTML，但 JS 里的
`ROLE_ORDER.indexOf(...)` 没有定义 ⇒ `ReferenceError` ⇒ `render()` 在渲染完
**第一个**图位后中断。

★ **症状极有欺骗性**：页面不白屏、不报错在控制台可见，
只是「内容少了一半」—— 验收看到的是「只有主图 section / 13 条」，
容易被误判成「数据源只有主图」或「筛选逻辑写错」。

⇒ 规矩：
1. 模板里的 JS 用到的**每一个常量**都要从 Python 注入（`@@ROLES@@` 这种占位符 + 断言全部替换完）
2. 生成后**断言没有残留占位符**（`assert k not in page`），并在注入后检查关键常量在 JS 里存在
3. 验收脚本要数**各分组的条目数**（`{主图:13, 附图:12, ...}`），
   只数总条数看不出「渲染中断」

★ 同类坑：模板里用 `str.format()` 会和 CSS 的 `{}` 打架（`KeyError: '--bg'`）
⇒ 用 `@@TOKEN@@` 占位符 + `str.replace()`，不要用 `.format()`。

## 61. ★ 美术素材块自带原图文字 ⇒ 与文字重叠的文字归美术层，别在块上再画活字 ★

**2026-11-02 实测**：用户看还原稿说「画面有问题」——同一处字**两套字形叠在一起**（重影）。

**根因**：美术素材块（`art`）是**从原图裁下来的**，块里**自带原图文字**。
渲染顺序是「美术层 → 文字层」⇒ 块上的原图文字 + 活字 = 重影。

**两条路都试过**：
- ① 把块里的文字像素**抠掉**（用底板重建补）→ 重影没了，
  但像素上比「原图直接贴」**差 2.1pp**（BPHN01 9.3% vs 7.2%）——底板重建 ≠ 原图像素。
- ② **不画活字**，被盖住的文字直接归美术层（原图裁切贴回）→
  重影没有 ✅、像素 0 损失 ✅，代价是那一处字不可编辑。

**⇒ 选 ②**，规则：**文字框被美术块覆盖 ≥50% ⇒ 归美术素材层**；
覆盖不足 50% 的仍做活字，并把块里那一小块文字**抠掉**（避免半截重影）。

**规矩**：
- **别用「重叠就整块丢弃」**——会把与文字轻微交叠的装饰（柠檬、花叶）整块丢掉。
  判定必须是「重叠**面积占比**」，不是「有交集」。
- **指标下降不一定是回归**——抠字版指标高 2.1pp，那是「作弊被拿掉了」
  （美术层直接贴原图 = 像素 0 损失）。**判要不要改，看视觉，不只看指标**。
- 归美术层要在**报告里标出来**，别让「活字率」悄悄掉。

## 62. ★ RGB/BGR 通道顺序：一个坑有两张脸 ★

**2026-11-02 同一天栽两次**：
1. `make_plate` 的 poly 回填：`plate_bgr[em] = fill[em]` —— `fill` 是在 **RGB** 数组上
   拟合的（`self.A` 来自 PIL，是 RGB），却写进 **BGR** 的 `plate_bgr` ⇒ **R/B 整个对调**。
   现象：红色底板上的字区被填成**蓝色**字形残影（底色 RGB(212,48,46) → 残影 RGB(45,46,209)，G 不变）。
2. `_ink_stats` 的 ref 解析：`r = [ref[5:7], ref[3:5], ref[1:3]]` = **BGR**，
   而 `pix` 是 RGB ⇒ 对**饱和色**（红字 #C4090C）解析成 (12,9,196)，色差 184 > tol 90
   ⇒ 掩膜全空 ⇒ **o_area = 0** ⇒ 评分退化成「|c_area − 0|」⇒ **永远选墨量最小的候选**
   （字重/描边一律选最细）。近白色 R≈B 看不出错，所以一直没被发现。

**规矩**：
- **一个模块里图像数组的通道顺序只有一个来源**（本项目：**cv2 那条线是 BGR，其余全是 RGB**）。
  新代码先确认 `self.A` / `self.O` / `self.P` / 渲染 cell 各自是什么。
- **hex 解析成 RGB 数组只走 `hex2rgb()`**，别在别处手写切片。
- **通道顺序的错误在近白色上不可见** ⇒ 必须用**饱和色**样本验一遍。
- **症状对照**：红底变蓝 ⇒ 通道交换；评分恒等于某个分量 ⇒ o_area=0 ⇒ 多半又是通道顺序。

## 63. ★ 美术块自带原图文字会污染「墨量类」寻优判据 ★

**2026-11-02 实测**：`font-weight` 候选 300/400/500/700/900 的评分
**恰好等于各自的活字墨量**（895/1215/1408/1793/2027），而不是「与原图墨量的差」——
因为 **原图(o_area) 与候选(c_area) 同时含美术块里那份原图文字**，
差值里原图那份抵消掉 ⇒ 只剩活字自己的墨量 ⇒ **候选越细分越低 ⇒ 永远选最细**。

**规矩**：
- 任何「原图 vs 重建」的墨量/像素统计类判据，**先确认重建侧与原图侧背景一致**。
  美术层、像素层、底板三层只要有一层多带了原图内容，判据就会退化。
- **「评分恒等于某个分量」= 判据退化信号**，看到就直接怀疑 o_area 被算成 0。

## 64. ★ 指标变差先二分，别急着改判据 ★

**2026-11-02 实测**：加了 4 处修复后，手机三张从达标掉到 8~15%（+1.9pp）。
直觉是「修复引入回归」，但真正的原因是**修复本身在拿掉作弊**。

**二分方法**（4 组跑完就定位）：
| 变体 | BPHN01 活字 diff |
|---|---|
| 全部修复 | 9.3% |
| 关掉「美术抠字」 | **7.2%**（= 修复前水平） |
| 关掉 `_ink_stats` 通道修复 | 9.29%（≈ base ⇒ 无罪） |
| 两个都关 | 7.18% |

**规矩**：
- **给每个新修复配一个「关掉它」的开关**（环境变量即可），回归时**四格跑**：
  base / 关A / 关B / 都关。**一次定位，不用猜。**
- **「指标变差」先分清是「真回归」还是「作弊被拿掉」**
  （美术层直接贴原图 = 像素 0 损失，抠字版必然更高 —— 这不是回归）。
- 二分比读代码快，但**必须先能复现**（同一张图、同一 spec、只改一个开关）。

## 65. 交付件上的每个数字都要能追溯到产物

**踩坑实例**：投递 PDF 里新增的「批量复刻验收」页，KPI 数字
（`125` / `1.49%` / `122/125` / 「3 张超过 8%」）**全写死在 HTML 模板里**。
补跑 5 张后实际变成 `1.55%` / `122/125`，页面还写着 1.49%
⇒ **交付物开始和自己的数据对不上** —— 而这一页的全部说服力就来自「数字是真的」。

**规则**
1. 交付页/报告里的**每个统计数字**都要从产物（`_report.json` / manifest / DB）
   **实时计算**，不写死常量。
2. 写死的地方改成 `{{PLACEHOLDER}}` + `str.replace`（**别用 `%` 格式化**，
   HTML/CSS 里的裸 `%` 会被吃掉 —— 本项目 `tb_board.py` 已踩过）。
3. 补跑 / 改数据后**必须重跑生成脚本**，让数字自动跟上；
   验收时要核对「页面上的数」==「产物里的数」。
4. 同理：**不要在交付件里留会失效的链接**。临时隧道域名
   （`*.trycloudflare.com`）进程一停就失效，HR 点开是「无法访问」，
   比没有链接更扣分 ⇒ 清理掉，或换成「投递时另附」这类不会失效的表述。

**一条自检**：交付前问自己「这页上的每个数，我能不能从产物里重新算出来？」
不能 ⇒ 就是写死的隐患。

## 66. 交付件里的「页数」也必须实测，不能写死

**踩坑实例**：给投递 PDF 插了第 07 页「批量复刻验收」⇒ PDF 从 **10 页变 11 页**。
但网站母版 / A/B/D/E 定稿 / 部署包 三处的文案里还写着
「作品集 PDF · **10** 页」「下载 PDF 版作品集（10 页）」，
而网站的下载按钮指向的 `assets/portfolio_2026.pdf` **真就是那份 10 页旧版**
⇒ **面试官在网站上下载到的 PDF，和 HR 收到的是两份不同的文件。**

**规则**
1. 页面里凡是描述产物规格的数字（页数 / 张数 / 体积 / 差异率），都要**从产物实测**：
   PDF 页数用 `pypdf` 数（`len(PdfReader(p).pages)`），不要手填。
2. 产物有多副本时，规格数字**只在源头生成一次**，其余地方引用同一份产物：
   母版里的页数标注由构建脚本从 PDF 实测写回（`swap_r15.py` 的 `pdf_pages()`）。
3. 验收要**交叉核对**：页面上写的页数 == PDF 实测页数 == 各副本的页数，三者相等才算过。

## 67. 产物有副本，就必须有「一个源 + 同步 + 校验」

**踩坑实例**：投递 PDF 改了，但 `网页\assets\` / `网页_版本_定稿\assets\` /
`网页_可部署包\assets\` / 投递目录里各躺着一份旧 PDF；
更狠的是 `网页_可部署包_20261102.zip` —— **打包脚本压根不产 zip**，
所以那个「投递时当附件 2」的 zip 从 11-02 起就一直是旧的
（没有 r15 对比图 + 塞着 10 页旧 PDF + 旧归因文案）。

**规则**
1. **先列出全部副本**：一份产物有几个落点就列几个（本地目录 / 打包件 / 引用它的页面）。
2. 改完产物跑**同步脚本**，让所有副本**逐字节一致**（md5 校验），不要靠人肉拷。
3. 打包脚本必须**产包**，且包内要**自检**（关键文件在不在、内容是不是最新版）。
4. 交付闸门要覆盖**副本一致性**（md5 相等），而不只是「文件存在」。

## 68. 「网页版」和「投递版」是两份独立文件，改一处必须动两处

**踩坑实例**：作品集「个人作品」段（pf 段）有 4 个槽位。
母版 `网页\index.figma.html` 引 `assets/p3_t1.jpg`，投递版 `投递版.html` 引 `img/p3_t1.jpg`，
**两份文件、两套图、两套文案**（实测两边的 `p3_t1.jpg` 字节数都不一样：111369 vs 113327）。
原来的换图脚本只改母版 + 重建网页，**既没管投递版、也没重出 PDF**
⇒ 用户把自己的作品放进去了，网站变了，**投出去的 PDF 还是占位图**。

**规则**
1. 动手前先确认：**这份内容出现在几个交付形态里**（网页 / 打印 PDF / zip / 静态包）？
2. 每种形态的**源文件**都要改，且改完要**重建该形态**。
3. 「换图/改文案」脚本的重建链要**包含所有形态**，每一步做 `rc` 检查 + 失败即停。
4. 文档里承诺脚本会做什么，就**让脚本真的做那件事**
   （本条是被投递说明里那句「跑 swap_pf.py 会重建…本 PDF」暴露出来的 —— 文档写了，脚本没做）。

## 69. 增量落盘的闸门，`--resume` 只认 key、不认图

**坑**：OCR 品类闸门用「逐张 append 的 jsonl + `--resume` 跳过已判过的 key」。
本项目真踩过：**手机 P2 五张错类图被换成真机图**（key 不变，文件换了）
⇒ jsonl 里那 5 条旧结果仍然在，`--resume` 直接跳过
⇒ **结果跑在旧图上，而闸门显示「125/125 已校验」** —— 错类图就这么混过了闸门。

**规则**
1. **凡是用「key + 增量结果」做闸门的，必须同时校验「结果记录的对象 == 当前对象」**：
   结果里存下被校验对象的**路径**，跑前/跑后都比一次
   （本项目：`verify_gate_integrity.py` 比 `result.path` vs `manifest.src`）。
2. 换图 / 重采 / 修数据之后，**必须重跑受影响的 key**，不能只补新增的。
   本项目的做法：启动器开跑前先做完整性自检，把「缺 key + 旧图 key」自动挑出来重跑
   （`run_ocr_gate.py --mode auto`）。
3. 闸门报告要打印**审了几个 / 覆盖了几个**，0 就要报警
   —— 「全绿」可能只是**根本没审到**（`os.walk` 对不存在的目录静默返回空，见 A-39）。

## 70. 交付有多个版本时，所有指标必须带「版本名」

**踩坑实录**
- 引擎每张产出**两个版本**：`index.html`（**活字版**，文字是 SVG 活字，可改价改文案）
  和 `index_px.html`（**像素层版**，字形改用原图裁切块，逐像素更准但不可编辑）。
- 验收统计**只读了 `live` 字段** ⇒ 全链路（作品集母版 / 定稿 A·B·D·E / 部署包 /
  投递 PDF / 状态板 / 总览网页）统一写着「**3 张超标**」。
- 实测真值（125 张全量，`_report.json` 的 `live` vs `px`）：

  | 版本 | 中位 | 达标 | 超标 | 最大 |
  |---|---|---|---|---|
  | 活字版 live | 1.55% | 122/125 | **3** | 17.33% |
  | 像素层版 px | **0.07%** | **125/125** | **0** | 3.63% |

  ⇒ 那 3 张在像素层版是 0.24% / 0.07% / 0.26% —— **像素层版一张都没超标**。
- ⇒ 「3 张超标」这句话**单独看是错的**。不写版本名，读者默认以为两种交付都超标。

**规则**
1. **交付产物有 N 个版本 ⇒ 每个指标（达标数 / 超标数 / 中位 / 区间）都必须带版本名**，
   表格和 KPI 并排展示两套，不允许只报其中一套。
2. **统计层**：唯一真相源（如 `batch_stats.py`）要同时算**每个版本**的口径
   （`med/ok/over` + `px_med/px_ok/px_over`），不要只算一套再让文案去推算另一套。
3. **文案层**：凡出现「N 张超标」「中位 X%」的句子，必须写成
   「**活字版** N 张超标 / **像素层版** 0 张超标」，并说明两者差别（可编辑 vs 不可编辑）。
4. **闸门层**：交付闸门的「必含文案」要**同时**校验两套口径的数字
   ⇒ 否则更关键的那套数字写错了没人拦（本次只校验活字版 = 漏检）。
5. **总览/对比网页**：每个 key 的 `out\<KEY>\` 下有几版渲染，网页就得贴几版
   （`_render_1x.png` 活字版 + `_render_px.png` 像素层版 + 原图 = 三栏）。
   ⚠ 漏贴的后果不是「少一栏好看点」，而是**读者只看到差的那一版**，
   对整批精度得出错误结论（本次就差点让 3 张超标盖住 125/125 全达标的事实）。

## 71. 分类体系必须落在配置层 + 数据层，不能只活在代码里的手写表

**踩坑实录**
- 用户一句「似乎你没做产品到分类呢」问出来的真实缺口（125 张批次）：
  | 层 | 当时的状态 |
  |---|---|
  | 采集词表 `tbflow.yaml fetch.categories` | 只到**品类**（美食速食/厨房小家电/…） |
  | 产品组 p1~p5 | 只以 **key 字符串编码**存在（`ALT2FO_P4_S2` → food/p4/附图2） |
  | 「p4 到底是什么产品」 | **唯一来源 = 网页生成器里手写的 `PRODKW` 字典**（代码层！） |
  | job 清单 | 只有 `name`（`"零食_p4_主图"`）编码串，无结构化字段 |
  | spec | **没有版式/族字段** ⇒「这张图是什么版式」查不到 |
  | 版式族聚类 | `tb_features.json` 是 10/27 的**旧批次**（LED 灯 21 主图+100 附图），125 张**从没跑过** |
- ⇒ 采集器 / 状态板 / 作品集三边各写各的，谁都不知道对方的分类。

**规则**
1. **分类定义放配置**（如 `product_catalog.yaml`），**不许放代码里的手写表**。
   换产品 / 加产品组只改配置，不动代码。
2. **job 清单回填结构化字段**：`cat_label` / `prod_group` / `product` / `shot_role` / `family`，
   并保留与旧 `name` 字段的**交叉校验**（不一致就报错，别静默）。
3. **★ 产品组必须用复合键（`品类_组`）**：只存 `p1..p5` 会把 **25 个产品组压成 5 个**
   （p1 在 food 是「零食组合装」、在 led 是「LED吸顶灯」）。踩过：状态板打出「5 个产品组」。
4. **★ 版式族用客观特征自动聚类，不人工起名**：复用 12 维特征
   （白底比/暗场比/照片比/文字行数/文字覆盖/饱和色块数/表格线数/边框标准差/明度/饱和度/纯色占比/宽高比）
   + StandardScaler + KMeans，主图与附图**分开聚**。
5. **★ k 的选择要罚「碎簇」**：只看 silhouette 会把 25 张主图聚成 13/5/3/2/1/1 ⇒
   出现 1 张的族没法用来筛选。⇒ 罚分 `score = silhouette - 0.12 × (只有1张的簇数)`，
   k 自然收敛到 12/9/2/2（主图）/ 61/26/13（附图）。
6. **★ 族标签用「相对全局基线的 z-score 偏离」，不用绝对阈值**：
   绝对阈值（如 `table_lines >= 6`）会让 9 个族里 8 个都带「参数表」⇒ 标签失去区分度。
   ⇒ 取该簇相对全局均值偏离最大的 2 个正向特征；都不明显才叫「通用」。
   簇成员 ≤2 张时追加「·小样本」标记（别假装它是个稳定族）。
7. **★ 对外文案里的分类数字也要进交付闸门**（几个品类 / 产品组 / 版式族），
   否则分类体系改了、作品集里的数字还是旧的。

## 72. 做「设计优化版」时，字色/字号/层级都得**实测重算**，不能照抄 spec

**背景**：复刻稿解决「能不能一模一样」，**优化稿**解决「这样更好」。
优化稿是在同一套版式骨架上重做四层（L1 文案 / L2 层级 / L3 可读性 / L4 统一）+ 一层工程（L5 可编辑）。
实测发现：照抄 spec 做优化，会把原图里**根本没被察觉的设计硬伤**原样保留，甚至改得更糟。

### 实测取证（LED 九宫格主图，8 个标签）
| 现象 | 实测值 | 说明 |
|---|---|---|
| 可读性 | 对比度 **1.29~2.16**，8/8 全不达标 | 白字压亮绿底（lum 0.397）**物理上限只有 2.3:1** ⇒ 必须自己算，不能靠肉眼 |
| 元数据失真 | spec 的 `fill` 记成 **投影色** | 原图是白字+绿投影，spec 记 `#67BE04`（绿）⇒ 活字版把白字渲成**绿字压绿底**（几乎隐形），而像素差异率只有 1.44% ⇒ **差异率会掩盖可读性缺陷** |
| 排版硬伤 | 字形比例 **0.08~1.88** | SVG `textLength` 锁字宽 + 字号随手给 ⇒ 有的压扁 20%、有的拉长 31% |
| 不可编辑 | 美术层文字是死的 | 「覆盖 ≥50% 的文字归美术层」是为「像素一模一样」设计的 ⇒ 优化版要**反过来**让它们回到活字层 |

### 规则
1. **★ 字色必须从原图重新采样，不信 spec**：底色 = 文字框外扩 4px 的**环带**中位色；
   真字色 = 框内「**离底色最远**的那簇像素」中位色（白字+投影 ⇒ 取到白）。
2. **★ 达标就保留原色，不达标才改**：优化是「修不达标」，不是「强行统一配色」。
   验收指标是「**字色种类不得变多**」，不是「≤3 色」。
3. **★ 改色时保留「原字色的色相」**：字色往往属于**面板的设计系统色**（蓝字在蓝色促销面板上），
   不是局部底色决定的 ⇒ 用底色的色相去重算，会把蓝字改成灰字。
   原字色没有颜色信息（白/灰/黑）时，才退回底色的色相。
4. **★ 层级用字重表达，颜色用对比度表达**：❌ 别按层级定色（原图标签底本身是深绿，
   按层级统一成深绿字 ⇒ **深绿字压深绿底**，优化越做越糟）。
5. **★ 字号按「自然字宽」反算，不做「统一字号」**：槽宽（标签底板）不能动 ⇒ 统一字号必变形。
   正解：`size = 槽宽(text_length) ÷ 自然字宽系数`，把**字形比例拉回 1.0**。
   ❌ 反过来（统一字号 + 同步重算 text_length）会把字压扁/拉长。
6. **★ 文案只统一「不一致的写法」**：同族写法本来就一致 ⇒ 零改动并如实记录。
   ❌ 无中生有的改写（如把全部「适用」改成「适配」）不是优化。
7. **★ 不动引擎的遮罩（`mask_color` / `tol`）**：默认遮罩已被全批验证过；
   一改 ⇒ 底板重建区域变了 ⇒ 促销条之类会被重建成噪点。
   涂抹的清理由「平色回填」单独负责。
8. **★ 平色回填用「原图的设计色」**：底板是**重建**出来的（实测：深色促销条在底板上被重建成深色、
   原图却是土黄）⇒ 涂底板色会穿帮。回填要涂**原图色**才等于设计稿。

### 配套的引擎开关（**默认关闭 ⇒ 存量批次零影响**）
| 开关 | 位置 | 作用 | 回归验证口径 |
|---|---|---|---|
| `opt_live` | `spec.text[].opt_live` | 该元素退出美术层、改画活字（可编辑） | 活字版/像素层版的**差异率必须与改动前完全一致** |
| `flat_text_bg` | `spec.flat_text_bg{id:{color,pad}}` | 把文字所在矩形**平色回填**，抹掉 inpaint 涂抹与投影 | 同上 |

### 优化版的验收口径（**不能沿用还原版那套**）
结构保真度 ≥95% / 对比度达标率 100%（大字 ≥3:1、小字 ≥4.5:1）/ 字形比例极差 ≤0.06 /
字重取值 ≤2 / 字色种类不得变多 / 文案规范率 100% / 活字占比 100%。
❌ **「字号取值数 ≤3」已作废**：多角色图（标题/价格/参数）本就该有多种字号，真正的硬伤是**字形比例**。

## 73. 像素差异率**测不出「隐形字」** —— 活字版必须有独立的体检口径

**来源**：用户反馈「我觉得活字版做的很差！！！」，而当时批次状态板写着「活字版达标 122/125」。
两句话直接冲突 ⇒ 说明**验收口径本身有洞**。

### 为什么差异率会骗人
| 缺陷 | 为什么差异率测不出 |
|---|---|
| 字渲成了底色（隐形） | **少画了东西** ⇒ 该区域像素差不大 |
| 字被压扁/拉长 | 墨迹面积小 ⇒ 像素差不大 |
| 底板残留原字白影 | 残影是**原图像素** ⇒ 与原图「一致」⇒ 差异率甚至更低 |

实测：ALTLE_P3_M 的 8 个标签里 3 个是绿字压绿底（肉眼完全看不见），
而整图差异率只有 **1.44%**。⇒ **差异率是「像不像」的度量，不是「好不好用」的度量。**

### 活字版必查的 6 项（`<诊断目录>\_live_audit.py`）
在**原图**和**活字版渲染图**上，对**同一批文字框**做同口径测量：

| # | 指标 | 判据 |
|---|---|---|
| M1 | 渲染对比度 | 字墨 vs 它所在底面的 WCAG 对比度（大字 ≥18px 且字重 ≥700 ⇒ 3.0，其余 4.5） |
| M2 | 原图对比度 | 同框在原图上的对比度（**设计稿真相**） |
| M3 | **对比度净降** | `原图对比度 − 活字版对比度 > 1` ⇒ **纯复刻回归**，与原图本身好坏无关 |
| M4 | 字形比例 | `text_length ÷ 自然字宽`（CJK 1.0em / ASCII 0.55em）；偏离 1.0 超过 0.06 = 压扁/拉长 |
| M5 | 死文字 | `art_covered=true` ⇒ 贴原图裁切 ⇒ 视觉对但**不可编辑** |
| M6 | 底色偏移 | 活字版底板色 vs 原图底色（最大通道差 > 30） |

★ **M3 是唯一能区分「复刻的错」和「原图就这样」的指标**，必须单列。
★ M2 单独看没有意义（那是设计稿的属性），但它决定了 M1 里有多少是「天生的」。

## 74. `spec` 的颜色字段可能是**取反**的，必须从原图重新采样

### 实测根因
`probe_layers.py::ink_color(mode="majority")` 把「**框内像素占比最大的簇**」当背景色。
文字带**粗描边/发光晕**时，框内占比最大的簇是**描边光晕色**，不是真底色
⇒ **底色与字色被取反**。

实测 ALTLE_P3_M t01（绿底白字标签）：
```
spec.bg   = #D6F4C5  ← 白+绿混合出的浅绿光晕（占比 20.7%）被当成底色
spec.fill = #67BE04  ← 真底色（占比 33.0%）被当成字色
框外邻域  = #64BE04  ← 真底色（离旧 fill 只差 3）
```

### 一个错误 ⇒ 三处受伤
| 引擎位置 | 用 fill 做什么 | 后果 |
|---|---|---|
| `make_plate()` `f = hex2rgb(t.get("mask_color", t["fill"]))` | 按 fill 挖字 | 挖掉绿底、挖不到白字 ⇒ **底板残留原字白影（重影）** |
| `make_plate()` 描边色同挖 | 挖描边 | 同上 |
| `build_html()` `fill="%s"` | 渲字色 | **绿字压绿底 ⇒ 几乎隐形** |

### 判定「取反了」的唯一硬判据
> **旧 fill 离「框外邻域色」（文字框上下各 4px 的中位色）≤ 25 ⇒ 旧 fill 其实就是真底色
> ⇒ bg/fill 被取反了。**

- ALTLE_P3_M t01：旧 fill 离邻域 **3** ⇒ 取反成立 ✔
- ALT2PE_P5_S4 t15：旧 fill 离邻域 **177** ⇒ 本来就对 ⇒ **不动** ✔

### 取色细则（三条都是踩出来的）
1. **底色** = 框内「离框外邻域色最近的**簇**」的中位色。
2. **字色** = 框内「离底色**最远的簇**」的中位色。
   ❌ 用「离底色最远的**像素**的中位色」会被抗锯齿像素拉偏（实测白字被取成浅绿 `#DAF5CB`）。
3. **对比度闸门**：旧配置本来就读不出来（<2.5）⇒ 必改；
   旧配置本来能读（≥2.5）⇒ 只有明显更好才改（避免把好的改坏）。

## 75. 修 `spec` 必须**同步修 `sweep` 候选集**，否则会被寻优覆盖

`spec["sweep"]` 里每个属性的**候选值是硬编码**的：

```json
{"marker":"适用创意灯","attr":"fill","values":["#67BE04","#68BA0D","#63BE0F","#69A712","#70BA14"]}
{"marker":"适用创意灯","attr":"font-size","values":[15,18,21]}
```

⇒ sweep 只能在**错的候选集**里挑最优（全是绿的）⇒ 修完 `spec.fill` 再跑，
sweep 照样会选回绿字。**必须同步改 sweep 条目**。

| 属性 | 怎么改 | 为什么 |
|---|---|---|
| `fill` | 把修正值放到候选**首位**（其余保留） | 让寻优能在正确色里挑 |
| `font-size` | **锁死为修正值**（单值） | 字号由「槽宽 ÷ 字符前进宽度」唯一确定；让 sweep 再挑会把字形比例打回原形——实测 sweep 把 18 选成 15 ⇒ 比例 1.02 变 1.23（又拉长） |

⚠ **按 marker（文字内容）分组改，不要按出现次序索引**：同名文字的 sweep 条目用 `occ` 区分，
而 `occ` 指的是 **HTML 里第几个 `<text>`**（不含美术层文字），与 spec 下标不是一回事。

## 76. Windows Chromium 对 SVG 文字走 LCD 子像素抗锯齿 ⇒ 字边缘有红蓝彩边

### 现象
活字版在 Windows 上渲染出来，字的边缘有**红蓝/青黄彩边**，肉眼判「发脏」。

### 实测（字墨区 R-B 通道差，越小越干净）
| | t00 | t01 |
|---|---|---|
| 默认（开 LCD AA） | 55 | 62 |
| `--disable-lcd-text` | **29** | **26** |
| 原图自身 | 40 | 37 |

放大对比（原图｜开LCD｜关LCD）证明：原图的字是**白字 + 绿色描边**（设计的一部分），
彩边是渲染器的锅；关掉 LCD AA 后**与原图肉眼几乎一致**。

### 修法
```python
args = []
if not os.environ.get("LAYOUT_RESTORE_LCD"):
    args += ["--disable-lcd-text", "--force-color-profile=srgb"]
browser = playwright.chromium.launch(args=args)
```
- 只影响文字边缘的抗锯齿方式，**不影响布局/坐标/图层**
- 回退开关：`LAYOUT_RESTORE_LCD=1`
- ⚠ 这一条**故意**会让活字版像素差异率变化；**像素层版不受影响**（字是位图裁切）

### ❌ CSS 层解决不了（实测 7 种方案，结果**完全相同**）
`-webkit-font-smoothing:antialiased` / `text-rendering:geometricPrecision|optimizeLegibility|optimizeSpeed`
/ `font-synthesis:none` / 整层 `svg` 关子像素 —— 全部无效。
⇒ **交付 PNG 用启动参数；源件包只能写进《还原规格说明.md》提示用户**。

### 顺带一条：原图的「描边」不是 bug
`spec.stroke` 记的就是原图字的那圈绿描边。**不要删 stroke**——
放大图证明原图就是「白字 + 绿描边」，保留 stroke 才能对上。

## 77. 寻优（sweep）**必须按元素唯一 id 定位**，不能靠「文字内容 + 出现序号」

### 症状
电商图里同一句文案**必然重复**（「小批定制」「SGS认证」「超级工厂」「￥ 12.9」…）。
重复越多，错位越狠：
- **一个标签空掉**（原图有字，成品里那块是空的）
- **另一个位置出现重影**（两个同名元素被写到同一处）

### 实测（ALT2PE_P5_S4 香水图，9 个「小批定制」）
```
spec t08:  box  = [32, 302, 73, 315]   ← 正确位置（第1行第1列的标签）
            x    = 286                  ← 被写成第4个「小批定制」的坐标
            base = 1048                 ← 同上
```

### 三个错位源（缺一不可）
| # | 位置 | 错在哪 |
|---|---|---|
| 1 | `autospec.py` 生成 sweep | **根本没写 `occ`** ⇒ 所有同名条目的 sweep 默认 `occ=0` ⇒ 全部作用在 HTML 里第 0 个同名 `<text>` 上 |
| 2 | `_sync_spec_from_html()` 回写 | 按「HTML 里同名 `<text>` 的出现序号」分配给 spec 里的同名元素；但归美术层（`art_covered`）和像素层（`px`）的文字**不画 `<text>`** ⇒ HTML 的 `<text>` 序列比 `spec["text"]` **短**，序号**整体错位** |
| 3 | `make_px()` 删活字 | 用 `re.sub(r'<text[^>]*>MARKER</text>', '', html)`，而 `re.sub` 会把**所有**同名 `<text>` 全删 ⇒ 同名文字在像素层版里**整块消失** |

### 正解：给每个 `<text>` 加唯一 id，sweep 一律按 id 定位
```python
# build_html：每个文字元素带上自己的 id
a = 'data-tid="%s" x="%d" y="%s" font-size="%s" ...' % (t.get("id"), ...)

# sweep：优先按 tid 定位，找不到才退回 marker + occ
pat = (r'<text[^>]*data-tid="' + re.escape(tid) + r'"[^>]*>' + re.escape(marker) + r'</text>')

# _sync_spec_from_html：优先按 data-tid 找元素
# make_px：按 data-tid 精确删除（连同该元素的 clipPath 色层）
```
★ `data-tid` 只是 HTML 属性，**不影响渲染**，客户打开源件包还能直接看出每个文字元素的 id（对改文案友好）。

### 存量 spec 怎么补 tid
`autospec.py` 生成 sweep 的顺序是**确定的**：对每个元素依次追加
`font-size → y → x → [stroke-width] → [font-weight] → [fill]`。
⇒ 照这个顺序把条目重新绑定到元素上即可，**不改动任何候选值**（零行为变化，只把「作用在哪个元素」定准）。

⚠ **绑定时只���「下一个」条目，���对不前向扫描**：
某个元素没有某属性时（比如没描边就没有 `stroke-width`），
前向扫描会一路找到**别的元素**的同属性条目 ⇒ 错绑 + 跳过别人的条目。
（踩过：只绑上 1 条，后面全乱。）

### 附带：`sweep` 的候选集也必须同步
修完 `spec.fill` / `spec.size` 还要同步 `spec["sweep"]` 里对应条目的候选值，
否则寻优会把修复**选回去**（详见铁律 54）。

## 78. 改完引擎后，**不许用新引擎渲「修复前」基线**

### 症状
修完引擎再回头做「修复前 / 修复后」对照，发现**基线是脏的**：
「修复前」那张图里，本该坏的居然是好的。

### 原因
新引擎已经修好了定位逻辑（铁律 56 的 `data-tid`）⇒ 用它渲出来的「修复前」
**天然带着修复效果** ⇒ 基线失真 ⇒ 对照结论无效。

### 正解：回退开关 + 原始 spec 重渲
引擎每改一处行为，就配一个**默认关闭**的回退开关：

| 开关 | 关掉什么 | 用途 |
|---|---|---|
| `LAYOUT_RESTORE_LCD=1` | 关掉 `--disable-lcd-text`（恢复 LCD 子像素抗锯齿） | 复现红蓝彩边 |
| `LAYOUT_RESTORE_NO_TID=1` | 恢复「文字内容 + 出现序号」的旧定位 | 复现重影 / 空标签 |

忠实的「修复前」环境 = **原始 spec** + **回退开关全开** + `--no-deliver`：
```bash
LAYOUT_RESTORE_LCD=1 LAYOUT_RESTORE_NO_TID=1 \
  rebuild.py --spec <原始spec> --out <基线目录> --no-deliver
```

### 原始 spec 从哪来
1. 首选 `specs/<KEY>.json.bak_*`（**修复器每次写盘前会自动留备份**，最新的那份就是原始态）
2. 没有 `.bak_` 的（从没被修过的）⇒ 直接用当前 spec
3. 两者都不是（spec 被旧版改过）⇒ 从原图重跑 `probe_layers → autospec → tb_vec --merge` 复现
   （autospec 补的 `tid` 在 `LAYOUT_RESTORE_NO_TID=1` 下完全失效 ⇒ 产物与原始批次等价）

### 顺带一条：全量跑批的基线备份也必须是「原始态」
批量脚本开跑时备份 `specs/`，如果备份的是**已经被修过的** spec，
后续每张都在「修好的版本上再修一遍」⇒ 不是对照实验。
⇒ 备份时优先取 `.bak_*`（原始态），没有才用当前 spec。

### 教训
**改引擎 = 同时改掉「历史产物的可复现性」**。
所以每改一处引擎行为，必须同时：
1. 留一个回退开关（默认关）
2. 保留原始 spec（`.bak_`）
3. 用「原始 spec + 回退开关」把旧行为重新渲出来，作为对照基线

## 79. 几何（字号/槽宽/位置）必须**测量闭环**修正，不许在 spec 层猜

### 错误做法（已实测证伪）
```python
size = text_length / 字符前进宽度      # 强制「字形比例 1.0」
```
看着很对：槽宽不变、字号按比例算 ⇒ 字形不被拉伸。

### 为什么是错的（A/B 三组实测，ALTLE_P1_M）
| 组 | 条件 | 活字版差异率 |
|---|---|---|
| A | 修复后 spec + 灰度抗锯齿 | 5.84% |
| B | 修复后 spec + 旧 LCD 抗锯齿 | 5.94% |
| C | **原始 spec** + 旧 LCD 抗锯齿 | **3.95%** |

⇒ 不是渲染器的问题，是 spec 改动让成品**涨了 2 个点**。

真正的原因：
```
OCR 框        456 × 102
实际墨迹      427 ×  74   ← 框比墨迹大一圈，左边还差 14px
```
- 「槽宽 ÷ 前进宽度」把字号从 105 压到 89 ⇒ 字比原图**矮 13%**
- `textLength` 仍锁在 456 ⇒ 字又比原图**宽 12%**
- 再把 sweep 的 font-size 候选**锁死** ⇒ 顺手把引擎自己的寻优能力也关掉了

### 正解：把「只打印」的校准升级成闭环
引擎里本来就有 `calibrate()`，它测的正是「原图 ink bbox vs 重建 ink bbox」，
但**只打印、不修正**；而 sweep 的候选只有 ±3（字号）/ ±2（位置）⇒ 修不了量级偏差。

```python
size       ×= 原墨迹高 / 重建墨迹高
textLength ×= 原墨迹宽 / 重建墨迹宽
x          += 原墨迹左 - 重建墨迹左
base       += 原墨迹下 - 重建墨迹下
```
四条配套规则：
1. **阻尼**（每轮只修 85%），防过冲振荡
2. **变差即整轮回退并停止** —— 校准只能让成品更好
3. **竖排/多行元素跳过**（原图墨迹高 > 2.5×宽）—— 整列 vs 一条横排的比例完全失真
4. **不能跳过 `px` 元素** —— px 只影响像素层版，活字版里它**仍然是文字**

### 推论
**「用经验常数推出来的目标」永远不如「量出来的目标」。**
探针给的 size/text_length/x/base 全是估计值；
能拿到的**实测**（原图墨迹 vs 重建墨迹）必须优先用。

## 80. 任何「降级/退化标记」必须**每轮重新判定**，不能只加不减

### 症状
`tb_px.py` 原来的判定：
```python
if rate > a.threshold and not t.get("px"):     # ← 只加不减
    t["px"] = True
```
⇒ 一个元素只要被降级过一次，就**永远**是像素层，哪怕修复之后它已经够好。

实测 ALTLE_P1_M 的 3 个元素**全部**带着历史 `px=True`，
而它们修复后的区域差异已经达标 ⇒ 白白牺牲了可编辑性。

### 连锁伤害
`calibrate()` 会跳过 `px` 元素 ⇒ 校准表**全空** ⇒ 一张都没校（本人踩过）。
⇒ 一个只加不减的标记，能让整套校准机制静默失效。

### 正解
每轮**先清历史标记，再重新判定**：
```python
for t in spec["text"]:
    if t.get("px") and not t.get("art_covered"):
        t["px"] = False
        t.pop("px_asset", None); t.pop("px_box", None)
# ↓ 然后才重新判定要不要降级
```
⚠ `art_covered` 的元素**不能清**：它们的 `px_box`/`px_asset` 是美术层要用的。

### 通则
**任何"上一次留下的状态"（降级标记 / 缓存 / 已锁候选）都要能被重置。**
否则修复一次之后，坏状态会被固化，且很难被察觉。

## 81. 交付页**禁止拼图**；图片按**真实宽高比**展示，每个角色块独立成行

### 症状（旧版总览页）
```css
.pair{display:grid;grid-template-columns:1fr 1fr 1fr}
figure img{aspect-ratio:1/1;object-fit:contain}     ← ← 罪魁
.fgallery{grid-template-columns:repeat(auto-fill,minmax(148px,1fr))}  ← 把几十个交付物拼成一面墙
```
把 851×1500 的竖版附图硬塞进 1:1 方框 ⇒ 上下留白、真实比例失真，
用户拿它**没法对比**（他原话：「不要做拼图 不然我不好对比」）。

### 正解：三层结构 + 自然比例
```
一级 品类（5）
  └ 二级 产品组（每组 5 张）—— 同产品的 5 张必须在一起
      └ 三级 角色块（主图 / 附图 / 附图2 / 附图3 / 附图4）—— 每块独立一行
          └ 并排三栏：淘宝原图 | 活字还原 | 像素还原
```
- 图片容器 `aspect-ratio` **按文件真实像素写**（构建时用 PIL 读出来），不写死
- 「修复前基线」做成**可切换的第 4 栏**，默认隐藏（否则 4 栏挤在一起）
- 每个角色块单独标注 **版式族 / KEY / 真实尺寸**
- 提供「组内按角色排 / 按版式族排」切换 ⇒ 满足「五个组单独分好类」

### 通则
**交付页的第一职责是「让人看出差别」，不是「把图都摆出来」。**
摆图的代价是失去对比能力。分组的第一维度必须是
**用户要对比的东西的归属**（同一产品），不是素材的形态（同一版式族）。

## 82. spec 里的数值字段**可能是 null**；`dict.get(key, 默认值)` 对 null **不生效**

### 症状
引擎崩在 `rebuild.py`：
```
File "rebuild.py", line 579, in build_html
    w = int(t.get("text_length", t["box"][2] - t["box"][0]))
TypeError: int() argument must be a string, a bytes-like object or a real number, not 'NoneType'
```
优化版批次 **23/86 张**全崩在这行。

### 根因
探针算不出槽宽时会写 **`"text_length": null`**（键**存在**、值为 null）。
Python 的 `d.get(key, default)` 只有在**键不存在**时才用 default；
键存在但值是 `None` ⇒ 返回 `None` ⇒ `int(None)` 崩。

### 为什么只有优化版崩，base 批不崩
- base 批：这些元素在 `cut_art()` 之后仍是 `art_covered=True`
  ⇒ `build_html` 走 `if t.get("art_covered"): continue` ⇒ **永远到不了 579 行**
- 优化版：脚本改了 `fill` / `weight` ⇒ `cut_art()` 的美术层判定变了
  ⇒ 部分元素被翻成 `art_covered=False` ⇒ 落到 579 行 ⇒ 崩

**实测回归**：把 base 批 86 份 spec 全跑一遍 `make_plate + cut_art`，
「会真正走到 579 行且 text_length 为 null」的元素 = **0 个**
⇒ 引擎这个 null 修复**不可能**改变此前任何成功渲染的产物（差异率零影响，不必全量重跑）。

### 正解
```python
_tl = t.get("text_length")
w = int(_tl) if _tl is not None else int(t["box"][2] - t["box"][0])
```
★ 不要写 `t.get("text_length") or 默认值` —— **值是 0 时语义会变**
（0 = 不加 `textLength`，`or` 会把它变成框宽）。

### 通则
**JSON 里的数值字段要当「可能缺失、可能为 null」来读。**
`d.get(k, 默认)` 只防「缺键」，不防「null」。
凡是 `int()` / `float()` 吃 spec 字段的地方，都要显式判 `None`。

## 83. 优化版**不能报差异率** —— 它与原图「故意不同」

优化版（档 A）做的是：字重分主次 / 字色按底色重算对比度 / 字号按自然字宽反算
⇒ **它本来就不是复原**，差异率对它没有意义（只会显示"变差了"）。

**该报的是可读性指标**：
| 指标 | 口径 |
|---|---|
| 对比度达标率 | 改后字色与底色的对比度 ≥ 4.5:1 的文字占比 |
| 字形比例（优化后） | `textLength / 自然字宽`，1.0 = 不压扁不拉长 |
| 字色种类 | 原图 11 色 → 优化后 8 色（配色收敛 = 层级清晰） |
| 改动处数 | 改了几个元素 |
| 结构保真度 | 版式骨架是否保持（档 A 要求 100%） |

**通用**：**任何"故意偏离基准"的产物，一律换指标体系，不要硬套差异率。**
差异率只用于「复原」类产物。
