> 每条固定四段：**现象 → 为什么会遇到 → 怎么解决的 → 以后遇到怎么办**。
> 目的不是记流水账，是让**下一个人（和下一个会话）不用再踩一遍**。

> **表面验收（文件在、链接对、数量对）查不出的坑，只有靠「产物内容比对」才能抓出来。**
> 本文里 P0-6、P0-7、P1-5 三条，全部是表面验收 100% 通过、实际全错的。

## A 组：引擎层（还原质量 / 渲染正确性）

### A-1 跨底色取色把字取成底色

**现象**
F11 参数档案卡：底图上半深下半浅，**白色**参数标题被还原成**深棕色**，跟背景糊在一起。

**为什么会遇到**
早期取色逻辑是「在文字 bbox 内，找离底色最远的像素，取它的颜色」——
这假设**整块区域只有一个底色**。一旦图里有多个色块（参数卡、促销条、色块分栏），
"离全局底色最远"的那个像素往往就是**另一种底色**，于是字的颜色被取成了邻近色块的底色。

**怎么解决的**
1. `probe_layers.py` 加 `col_bg_map()`：**逐列**估算局部底色（取参照框外的上下条带做背景采样），
   不再用一个全局底色。
2. 加 `bg_split()`：连续切分检测硬边界，判断某个 bbox 内是不是**跨了色块**。
3. 加 `ink_stroke_color()`：用**笔画厚度**判据取墨色 —— 文字笔画窄，色块边缘贯穿整个 bbox。
4. `ink_color()` 的 majority 分支改成「老路 + 厚度路**冲突仲裁**」。

**以后遇到怎么办**
- 记住这条判据的**适用范围**：**底色是局部量**。任何「取色」「对比度」「找主色」的判据，
  只要目标区域可能跨色块，就必须先做局部背景估计，不能用单一全局值。
- **新判据先当「仲裁者」不当主力**。第一版如果直接让厚度判据当主判据，
  照片底上的字会集体被取浅（照片纹理误判成笔画）。老路保留、新路仲裁，两边冲突才升级。
- 复用方式：`col_bg_map()` / `bg_split()` / `ink_stroke_color()` 三个函数已进开源仓库，
  换素材直接调，别重写。

### A-2 GBK 控制台 crash

**现象**
批量跑到一半整轮崩，栈顶是 `UnicodeEncodeError: 'charmap' codec can't encode character`，
崩的字符通常是中文或 `®` 这类符号。

**为什么会遇到**
Windows 控制台默认编码是 **GBK**（cp936）。引擎日志里有中文和符号，
Python 用 GBK 往 stdout 写就抛异常。子进程**没有继承**父进程的修复。

**怎么解决的**
- 每个脚本开头加：
  ```python
  try:
      sys.stdout.reconfigure(encoding="utf-8", errors="replace")
      sys.stderr.reconfigure(encoding="utf-8", errors="replace")
  except Exception:
      pass
  ```
  （`probe_layers.py` / `autospec.py` / `tb_vec.py` / `tb_px.py` / `rebuild.py` 全部补齐，
  **开源仓库那份同步改了**。）
- 起子进程时注入环境变量 `PYTHONIOENCODING=utf-8`（`tb_run.py` + skill 的 `common.child_env()`）。

**以后遇到怎么办**
- **Python 脚本只要会打中文，第一行就 reconfigure**，不要等报错再补。
- 注意 `errors="replace"`：宁可把字符替换掉，也别让整轮崩。
- 子进程也要单独注入 —— 环境变量是最省事、最不会漏的一层。

### A-3 子进程 PIPE 死锁

**现象**
批量跑到一半**完全不动**，不报错、不退出。任务管理器里 python 进程还在，CPU 0%。

**为什么会遇到**
父进程用 `subprocess.PIPE` 接子进程 stdout，但**父进程不读**。
Windows 管道缓冲约 **64KB** —— 子进程日志写满 64KB 后阻塞在写，
父进程在等子进程退出 → **互相等死**。日志越长越容易触发（所以常常是「跑了一半」才死）。

**怎么解决的**
子进程输出**直接写日志文件**，不用 PIPE：
```python
with open(log, "w", encoding="utf-8") as fh:
    subprocess.call(cmd, stdout=fh, stderr=subprocess.STDOUT)
```
`run_batch.py` / `verify_all.py` 都是这个模式，日志在 `<work>/logs/b_<KEY>.log`。

**以后遇到怎么办**
- **记住这条硬规则：不要用 PIPE 接长输出的子进程。**
  要么直接落文件，要么起线程专门读。落文件更好 —— 还能留证据。
- 怀疑死锁时先看：子进程是不是卡在写 stdout。`Ctrl+C` 能打断就说明在等 I/O 而不是算不动。

### A-4 报告脚本在构造列表时就崩了

**现象**
`report.py` 跑到最后一步崩：
```
ValueError: unsupported format character '?' (0x662f) at index 20
```
**但 stdout 上的达标率数字全都打完了**，看着像成功。实际 `batch_report.md` 根本没落盘，
磁盘上躺着的是**上一次跑的旧文件**（还缺「全部文字已像素化」这一口径行）。

**为什么会遇到**
中文格式串里有个字面 `%`：
```python
"| ⚠ 全部文字已像素化（像素层 0% 是构造的） | %d |" % len(trivial)
```
`0% 是` 里的 `%` 被 Python 当成格式说明符开头 → 解析到非法的 `%是` → ValueError。

**怎么解决的**
字面 `%` 写成 `%%`：
```python
"| ⚠ 全部文字已像素化（像素层 0%% 是构造的） | %d |" % len(trivial)
```

**以后遇到怎么办**
- **凡是「中文文案 + % 格式化」混排，所有字面百分号一律 `%%`。**
  写完立刻跑一次，确认 `.md` 文件的 **mtime 真的更新了**，别只看 stdout。
- 这条的教训比 bug 本身重要：**stdout 打印成功 ≠ 产物落盘成功**。
  报告类脚本要**先落盘再打印「报告 -> xxx」**，或者至少在打印前确认写成功。

### A-5 对比站热力图张冠李戴

**现象**
对比站 50 张卡片的「差异热力图」**内容完全一样**（都是 M01 的那张）。
实测：50 个 `*_hm.png` 文件，**唯一内容只有 1 个**。
而真源 69 张热力图里有 65 个唯一内容 —— 说明源是对的，是站点配错了。

**为什么会遇到**
`_find_heatmap()` 原本的逻辑是「在交付根目录里遍历，找到第一个
`*_差异热力图_活字版.png` 就返回」。而遍历顺序是**目录名排序**，M01 排最前 →
**每张卡片拿到的都是 M01 的热力图**。

**为什么所有表面验收都没发现**
- 文件数对：50/50 ✅
- 链接对：`img_hm` 字段都有值 ✅
- 按钮能点、能显示、图能放大 ✅
- **内容对不对：没人查** ❌

**怎么解决的**
改成**按 KEY 精确命中**交付包目录：
```python
if not (sub == key + "_像素级还原" or sub.startswith(key + "_")):
    continue
```
再加一层兜底：用原图文件名主干（如 `tb_main_016`）再找一次，防目录命名不统一。
最后在 `make_site.py` 末尾加**内容级自检** —— 对所有热力图算 MD5，出现重复就报错退出：
```python
if dup:
    print("!! 热力图张冠李戴 %d 处" % len(dup))
    return 3
```
修完实测：**50 张内容互不相同**。

**以后遇到怎么办**
- **凡是「一个产物对应一批输入」的映射，绝不能靠「遍历找到第一个」。**
  必须用**输入的标识**（KEY / 编号 / 文件名）去定位产物。
- **交付前的自动验收要加一条「内容唯一性」检查**：同批次产物两两哈希，
  重复即报错。很多「看起来没问题」的 bug 只有这一条能抓。
- 泛化：批量还原、批量导出、批量截图，凡是 `for key in keys: find_artifact(key)`，
  `find_artifact` 都必须**按 key 定位**。

### A-6 对比站热力图全丢

**现象**
「差异热力图」按钮点开，显示的还是活字版，50 张热力图一个都没有。

**为什么会遇到**
交付包写在**两个不同的地方**：
1. `out/<KEY>/deliver/<KEY>_像素级还原/` —— 公开仓库版引擎写这里
2. `<paths.deliver>/<KEY>_像素级还原/` —— 共享引擎写这里（作品集目录）

查找函数只写了路径 ① → 路径 ② 下的全丢。

**怎么解决的**
两条路径都找（见 A-5 的代码）。

**以后遇到怎么办**
- **「产物可能落在哪」要一次性列全，并写进同一个查找函数**，
  别指望「我明明存到那儿了」。引擎换版本、目录重组都会让某一处失效。
- 排查手法：`Get-ChildItem <交付根> -Recurse -Filter '*热力图*'` 先看**真源在不在**，
  分清是「没生成」还是「没找到」。

### A-7 验收脚本永远返回 0

**现象**
`verify_all.py` 跑完打印了一堆 `rc=1`（不一致），但脚本退出码是 0，
上层 pipeline 继续往下跑，最后显示「全部步骤结束」。

**为什么会遇到**
`verify_all.py` 结尾写死 `return 0`；而 `verify.py` 本身是**会**用非 0 退出码表达不一致的。
中间的汇总层把语义吞了。

**怎么解决的**
统计失败数，按失败数返回：`return 0 if fail == 0 else 1`；
同时把跳过的（没产出 `index.html` 的）**打印出来**，静默跳过 = 少验了一半还以为全验了。

**以后遇到怎么办**
- **任何汇总/编排层脚本，退出码必须由子步骤聚合而来**，不能写死。
- 编排层要能区分三种状态：成功 / 失败 / 跳过。**跳过必须报数**。

### A-8 相对路径输出直接 crash

**现象**
`python report.py --out 报告.md` → `FileNotFoundError: [WinError 3] 系统找不到指定的路径: ''`
（`os.makedirs('')` 抛的）。

**为什么会遇到**
```python
os.makedirs(os.path.dirname(md), exist_ok=True)
```
`md` 是相对路径时 `dirname` 是**空串**，`makedirs('')` 直接报错。
而这个用法就写在脚本自己的 docstring 里。

**怎么解决的**
先转绝对路径再取目录：
```python
d = os.path.dirname(os.path.abspath(md))
os.makedirs(d, exist_ok=True)
```
JSON 输出路径同样处理。

**以后遇到怎么办**
- **凡是 `os.makedirs(os.path.dirname(p))`，一律先 `os.path.abspath(p)`。**
  这是个通病，不止这一个脚本。
- 更省事的写法：`os.makedirs(os.path.dirname(os.path.abspath(p)) or ".", exist_ok=True)`。

### A-9 子进程用了错的 python

**现象**
全流程跑完，出的图全是空白 / 报 chromium 缺失。

**为什么会遇到**
`pipeline.py` 用 `sys.executable` 起子脚本 —— 也就是**当前跑 pipeline 的那个解释器**。
本机 `Python314` 没装 chromium，只有 `Python311` 有。
配置里明明写了 `engine.python`，但 pipeline 没用它。

**怎么解决的**
`pipeline.py` 的 `step()` 改成接收 `py` 参数，用 `C.py_exe(cfg)` 取配置里的解释器。

**以后遇到怎么办**
- **凡是本机有多个 Python，环境必须写进配置，所有子进程都从配置取**，不要用 `sys.executable`。
- 这条跟 A-2 一样是「子进程不看父进程的修复」——
  **父进程环境 ≠ 子进程环境**，配置/环境变量都要显式传。

### A-10 选片配额超出目标

**现象**
传 `--target 30`，实际选了 35 张。

**为什么会遇到**
`allocate(total, sizes)` 里 `base = [max(1, total // n)] * n`：
当 `total < n`（簇数比目标还多）时，每份至少 1 → **总和超过 total**。
另外 `fps_select(recs, k)` 在 `k=0` 时会走进采样逻辑并返回 **1 条**，不是 0 条。

**怎么解决的**
- `allocate()`：加 `total == 0` / `n >= total` 两个分支，并加「总和必须严格等于 total」的兜底修正。
- `fps_select()`：开头加 `if k <= 0: return []`。

**以后遇到怎么办**
- **配额分配函数必须有一条断言：返回值之和 == 请求值。** 不等就是 bug。
- 任何「至少 1」的兜底都会**破坏总量守恒**，加兜底时必须同时加总量修正。

### A-14 描边宽度候选集不够宽

**现象**
带描边的标题字还原出来描边偏细，对不上原图。

**为什么会遇到**
`autospec.py` 的 `stroke-width` 候选集是 `1,2,3,4,5,6`。
但实测原图描边**单侧** 4~5px，SVG 描边是**对称**的，要画到 8~10 才等效。

**怎么解决的**
候选集扩到 `1,2,3,4,5,6,8,10,12`。

**以后遇到怎么办**
- **做参数寻优时，候选集要覆盖「实际值的 2 倍以上」**，否则天花板卡死。
  先量一遍原图实际值，再定候选集范围。
- 参数寻优找不到解时，先怀疑**候选集没覆盖真值**，而不是判据错了。

### A-15 像素层版改成条件产出

**现象**
有些交付包里没有 `index_px.html` —— 而交付口径是「活字版 **或** 像素层版任一达标」，
少一个版本就少一条达标路径。

**为什么会遇到**
`rebuild.py` 里像素层版在条件分支下生成（某些情况不产出）。

**怎么解决的**
改成**无条件产出** `index_px.html`。

**以后遇到怎么办**
- **交付物清单里的每个文件，要么无条件产出，要么在交付说明里写清楚"什么情况下没有"。**
  验收脚本要按实际产物目录遍历，不要按预期清单假设。

## B 组：工程 / 编排层

### A-11 坏配置静默降级

**现象**
`config.yaml` 开头误写成 Python docstring → YAML 解析失败，
但 `doctor.py` 还报「可以跑」，脚本拿着默认路径跑，**全跑错地方**。

**为什么会遇到**
`load_cfg()` 读 YAML 失败时 `except: pass` → 退回内置 `DEFAULTS` → 路径全是空/相对 → 看起来在跑。

**怎么解决的**
解析失败**直接退出**：
```python
except Exception as e:
    sys.stderr.write("[cfg] 配置解析失败：%r\n  文件：%s\n" % (e, p))
    sys.stderr.write("[cfg] 修好再跑 —— 静默用默认路径比崩更糟\n")
    raise SystemExit(2)
```
`config.local.yaml` 同样处理。

**以后遇到怎么办**
- **坏配置要崩，不要静默降级。** 崩了 1 秒就知道；静默降级会浪费几小时跑错地方。
- 配套：`doctor.py` 必须**真的解析一次配置**，不能只看文件在不在。
- 这条是本项目的一条**通用原则**：任何「读配置」的地方，失败即退出。

### A-12 验收清单硬编码样本

**现象**
项目侧 `verify.py` 里写死了 `ITEMS = [("R1_...","R1_...",...), ..., ("R6_...",...)]` —— 只有 6 个样本。
但实际交付包有 **67 个**。也就是说，**67 个包从来没被验收过**，
而验收脚本每次都报「全部一致 [OK]」。

**为什么会遇到**
早期只有 6 张 R1~R6 样本，就把样本清单写进了代码。跑批扩到 50 张、交付扩到 67 个时，
**验收没跟着改**。

**怎么解决的**
- 开源仓库里那份 `verify.py` 重写成**通用版**：验收包由 `--pack` 参数传入，
  原图从 `_spec.json` 的 `src` 读，没有硬编码清单。
- skill 的 `verify_all.py` **遍历实际产物目录**（`out/*/index.html`），不再读样本清单。

**以后遇到怎么办**
- **验收范围 = 实际产物目录，不是你记得的那几个样本。**
  硬编码的样本清单一定会随着规模扩大而失真。
- 检查手法：`产物数量` vs `验收数量`，两个数对不上就是漏验。
- 这条和 A-7 是同一族：**验收的「范围」和「结果」都可能是假的，而且表面看不出来。**

### A-13 流水线吞掉子步骤失败

**现象**
`pipeline.py` 里 `step()` 拿到了 `rc`，但除了第 ①② 步外都**没检查**，
最后固定 `return 0` + 打印「全部步骤结束」。

**怎么解决的**
收集每一步 rc，任一步失败 → 最终 `return 1`；并在打印「结束」时区分成败。

**以后遇到怎么办**
- **编排层的退出码 = 各子步骤退出码的聚合**，永远不要写死 0。
- 「全部步骤结束」这句话本身就有歧义，改成「全部步骤结束，其中 N 步失败」。

### A-13b make_site 的 rmtree 没有护栏

**现象 / 风险**
`make_site.py` 直接 `shutil.rmtree(out_root)`。`--out` 指错一个目录 → 整个目录被删，不可恢复。

**怎么解决的**
删之前先确认这**确实是个站点目录**：目录里必须有 `index.html` / `data.json` / `full` / `thumbs` 之一，
否则报错退出，宁可不删。

**以后遇到怎么办**
- **任何递归删除前，先断言目标「长得像」该删的东西。**
  一条断言换一份不可逆的保险。

## C 组：方法论（不是 bug，是「怎么做才对」）

### A-18 达标率口径混着报

**现象**
只报一个「达标率 98%」，听着很好；但它同时混了两种完全不同的东西。

**为什么会遇到**
交付本来就给**两个版本**（活字版 + 像素层版），达标口径是「任一达标」。
但**像素层版会把每个字换成原图裁切块** —— 逐像素相同，差异率 0%，
**那是构造出来的，不是能力**。混着报 = 把构造出来的结果算成真本事。

**怎么解决的**
**三条口径必须分开报**（`report.py` 固定输出这三行 + 一条警示）：

| 口径 | 50 张实测 | 含义 |
|---|---|---|
| 交付达标率（活字或像素任一 ≤8%） | 49/50 = **98.0%** | 「这批能不能用」 |
| 活字版达标率（全部） | 36/50 = **72.0%** | 「文字真用替代字体重建能到多少」 |
| 有效复刻达标率（文字元素 ≥3） | 24/38 = **63.2%** | 「排除纯产品照后还剩多少」 |

外加两条必报：
- **⚠ 全部文字已像素化的样本：36 张** —— 它们的像素层 0% 是构造的，不能当达成度。
- **艺术字（活字超差 / 像素达标）：13 张** —— 这批的处置还没定（待拍板：归美术素材层）。

**为什么「有效复刻」要剔除文字 <3 的**
12 张文字元素 <3 的图，多是纯产品照，**差异率≈0 是因为没活干**，不是复刻能力强。

**以后遇到怎么办**
- **报任何达标率之前，先问「这个数字里有多少是构造出来的」。**
- **多版本交付必须分开报「哪个版本达标」，也要报「哪些样本是构造出来的」。**
- **数字全部写进报告文件**（不是只打印到 stdout），并留 mtime 证据（见 A-4）。

### A-19 随机选片稀释了达标率

**现象**
一开始随机抽 50 张，跑出来的达标率忽高忽低，代表不了工具真实水平。

**为什么会遇到**
随机抽出来的 50 张里有大量长得很像的（同类版式）→ 达标率被相似样本稀释。

**怎么解决的**
**按版式族聚类分配配额 + 簇内最远点采样（FPS）**：
- 主图全要（21 张，覆盖 4 个簇）
- 附图按簇大小比例分配 29 张名额到 8 个簇
- 簇内用最远点采样挑互相差异最大的

两次独立跑出的 50 张**完全一致**（可复现）。

**以后遇到怎么办**
- **测能力就抽样，测能力就要抽「有代表性的样本」，不是随机样本。**
- 配额分配必须**总量守恒**（见 A-10）。
- FPS 采样前先标准化（z-score），否则量纲大的特征主导距离。

### A-20 艺术字结论必须分区复算

**现象**
「艺术字做不了」这个结论差点就下了 —— 但下结论前一看非文字区差异率，
**14 张里只有 7 张真有 85px+ 的艺术字元素**，其中 **S28 是纯工程缺陷**（不是素材限制）。

**为什么会遇到**
用整图差异率下结论 → 把**工程缺陷**（渲染没对齐）误判成**素材限制**（字体找不到）。

**怎么解决的**
下任何「素材限制」类结论之前，必须**分区复算**：
1. 先切出**非文字区**，单独算差异率；
2. 只有非文字区也高，才说明是别的问题；
3. 再判断是「素材不存在」还是「工程没做对」。

**以后遇到怎么办**
- **「做不到」这种结论，必须先排除「没做对」。** 先分区，再定性。
- 工程缺陷和素材限制的解法完全不同 —— 混了就会去要错的东西。

## C 组（续）：多批次 / 选片（2026-10-31 多品类批次新增）

### A-23 「组」不等于「同一商品的主图+附图」★

**现象**
要「每品类三组主图和附图」时，很容易默认「一组 = 同一个商品的主图 + 附图」。

**为什么会遇到**
抓图走的是**通道 B**（必应图片索引 → alicdn 直链 → 下载 → 程序筛选），
拿到的是**散图**，**没有任何商品结构信息** —— 不知道哪张附图属于哪张主图。
（通道 A 能按商品结构组织，但要用户开带登录态的浏览器走 CDP 9222。）

**怎么解决的**
「组」重新定义为 **同品类下视觉特征相近的一簇图**（版式族）：
- 每品类**独立**跑 12 维特征 + KMeans 聚类
- 组内**离簇心最近**的那张当主图，其余当附图

**⚠ 这个定义必须写进交付说明**，否则看图的人会以为「附图是这张主图的详情图」，
从而对还原结果的语义关系产生误判。

**以后遇到怎么办**
- 任何「抓回来再分组」的需求，先问一句：**分组依据是产品语义还是视觉相似？**
  通道 B 只能给后者。要前者就必须走通道 A（要用户配合开浏览器）。
- **别在文档里含糊**：「组 = 版式族」和「组 = 同商品」对使用者是完全不同的承诺。

### A-24 多批次共存：profile 隔离 + KEY 前缀隔离

**现象**
同一个 skill 要同时服务多批（原图库不同、品类不同），
如果所有批次共用一份 `config.local.yaml`，改一次就把上一批的路径搞乱。

**怎么解决的**
1. **profile 机制**：每个批次一份 `config.local.<profile>.yaml`（**不入库**），
   用环境变量 `LAYOUT_RESTORE_PROFILE` 切换（子进程靠环境变量继承）。
2. **KEY 前缀隔离**：批次之间共用工程根，但 KEY 前缀不同
   （`M01`/`S01` vs `POT01`/`ELE01`/`PER01`/`FOO01`）→ `out/`、`specs/` 互不干扰。
3. **日志/站点目录独立**：`paths.work` 分开、`site.dir` 不同名
   （⚠ 同名会把上一批的对比站整个覆盖掉）。

**以后遇到怎么办**
- **同一套工具服务多批数据 → 用 profile 隔离配置，不要来回改同一份。**
- **共用输出目录时，KEY 必须带来源前缀** —— 否则两批的产物会互相覆盖。
- **任何「输出目录」类的配置项，先查一下会不会覆盖别人的产物。**

### A-25 特征提取要缓存（每张 1.5s 的 OCR）

**现象**
按品类分组选片跑超 10 分钟超时。

**为什么会遇到**
12 维特征里有 `text_lines` / `text_cover` → 每张都要跑一遍 OCR。
实测分段耗时（800×800 图）：Laplacian 0.01s / erode 0.00s / Hough 0.06s
→ **OCR 单独就 5.17s**（原实现对小图会**放大 2 倍**再 OCR = 1600×1600）。
引擎初始化另计 2.66s（一次性）。

更要命的是**本机 CPU 已被占满**（交易系统 sim_runner + AgentBus + 其他 harness 常年跑），
总 CPU 100% → 我的进程只能分到一半 → 墙钟 16s/张 → 221 张要 1 小时。

**怎么解决的**
1. **特征缓存**：按品类落盘 `<work>/_feats/feats_<cat>.json`，
   以「输入文件集合是否一致」判缓存有效性 → 改配置重跑秒级完成。
   ⚠ 特征里有 numpy 标量（`intc`/`float64`），`json.dump` 会炸
   → 必须挂 `default=lambda o: o.item()` 降成 python 标量。
2. **三档 OCR 模式**：
   | 模式 | 做法 | 耗时/张 | 用途 |
   |---|---|---|---|
   | `proxy`（默认） | 形态学估「文本行」：自适应阈值 → 连通块 → 筛扁宽笔画 → 按 y 合并成行 | ~20ms | 只用于**聚类** |
   | `scale` | 先缩到 700 再 OCR（zoom=1） | ~2.2s | 要准的聚类 |
   | `full` | 原样 OCR | ~5.2s | 精确场景 |
3. `proxy` 的代价：`text_lines`/`text_cover` 是**估计值**。
   → **只用于分组，不用于任何对外指标**（达标率仍用真实 OCR 的引擎指标）。

**以后遇到怎么办**
- **聚类用的特征不需要「认字」，只需要「那块图文字密不密」** →
  别用 OCR 当特征提取器，用形态学代理，快 100 倍。
- **特征提取是「慢」这件事要在设计期就算进去**：一张 5s × 200 张 = 一个多小时。
- **先分段计时再优化**：我一开始以为慢在 cv2，实测 cv2 部分加起来 < 0.1s，
  瓶颈 100% 在 OCR。**不测就优化 = 优化错地方。**
- **本机 CPU 是共享资源**：跑批前先看 `Get-Counter '\Processor(_Total)\% Processor Time'`，
  100% 就说明有别人在抢，jobs 别开大。
- **任何跑 OCR / 跑模型 / 跑网络的特征提取，都要缓存。**

## D 组：环境 / 平台

### A-21 PS 5.1 `Tee-Object` 存的是 UTF-16LE

**现象**
`cmd 2>&1 | Tee-Object -FilePath xxx.log` 存完，后台任务的 `task_output` 里内容完全正常，
但用读文件工具打开全是乱码（`��` + 单字节中文）。

**为什么会遇到**
PowerShell 5.1 的 `Tee-Object` / `Out-File` 默认写 **UTF-16LE（带 BOM）**，
读文件工具按 UTF-8 解码 → 必然乱码。**不是脚本输出坏了，是编码读错了。**

**怎么解决的**
读的时候显式指定编码：`Get-Content 'xxx.log' -Encoding Unicode`。
（写的时候别手动加 `-Encoding`，让 `Tee-Object` 自己定，避免混编码。）

**以后遇到怎么办**
- **判读优先级：同一段输出同时出现在任务输出和落盘日志里，先信任务输出**（实时 stdout，无编码转换）。
- 看到乱码先怀疑编码，**别据此怀疑管道/脚本有问题，也别急着重跑** ——
  重跑会覆盖生成时间，污染基线口径。

### A-22 Windows 安全策略拦嵌套目录拷贝

**现象**
`Copy-Item` 把一个目录递归拷到目标路径，报「recursive write/delete target cannot be verified」。
**字面路径**可以，**变量/计算出来的路径**不行。

**为什么会遇到**
本机安全策略对递归写/删做目标校验，变量路径无法静态判定。

**怎么解决的**
- **能用字面路径就写字面路径。**
- 删除走 `rm -- <target>`（走 mavis-trash，可恢复），**不要用 `Remove-Item`**（无回收站）。
- 写 agent 运行时数据目录（`~/.mavis/` 那类）会被拦时，用写文件工具而不是 shell 重定向。

**以后遇到怎么办**
- **被拦时先换写法，别硬刚**：字面路径、换个目录、用文件工具写入。
- 删除一律优先可恢复方案；`Remove-Item` 在这台机上等于永久删除。

## E 组：三条检查清单

### 跑批前

1. `doctor.py` 跑一遍 —— **配置能解析**、python 带 chromium、原图库有图、簇表在。
2. `pick.py --dry-run` —— 看配额分布合不合理，选中的图**是不是互相不一样**。
3. 确认用的解释器是配置里那个（`engine.python`），不是 `sys.executable`。

### 跑批中

4. **子进程输出落文件，不走 PIPE**（A-3）。
5. **每个子进程注入 `PYTHONIOENCODING=utf-8`**（A-2）。
6. 看**日志文件**，不要只看终端（终端滚走了就看不到了）。
7. 进度 JSON 落盘 —— 断了能续，不用从头跑。

### 交付前（这一步最容易漏，最容易错）

8. **产物数量 vs 验收数量**要对上（A-12）。
9. **同批次产物做哈希唯一性检查** —— 重复即张冠李戴（A-5）。
10. **验收脚本的退出码非 0 就是没过**，编排层要聚合退出码（A-7 / A-13）。
11. **报告文件的 mtime 确认更新** —— stdout 打完了不代表落盘了（A-4）。
12. **多版本达标率分开报 + 标出构造出来的样本**（A-18）。
13. **对比站要人工点开 3~5 张**看内容对不对，不能只看文件数。
